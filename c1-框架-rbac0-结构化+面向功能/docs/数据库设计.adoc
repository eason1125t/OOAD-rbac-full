== 陈氏 ER 图

核心视图表达员工、角色、权限和两组多对多联系。扩展视图表达组织归属、管理范围、系统归属和组织权限配置。扩展图中同名实体在不同分区重复出现，指向同一个概念实体。

image::01-核心授权.svg[核心授权陈氏 ER 图]

image::02-组织与授权范围.svg[组织与授权范围陈氏 ER 图]

矩形表示实体，菱形表示联系，椭圆表示属性，下划线表示主标识。白话读法如下。

* 员工与角色、角色与权限均为零到多对零到多。
* 每个业务系统属于一个组织，每个组织可有多个系统。已匹配员工归属一个公司或一个部门，部门经上级关系归属公司。待匹配员工可暂缺组织，确认前无法登录和参与授权。
* 每个业务权限定义属于一个业务系统。管理权限可不关联业务系统。角色和权限定义可归属一个组织，全局定义采用全局范围。
* 组织与权限配置是多对多。一条配置描述该组织对某个权限的开放或停用状态，权限 ID 已确定业务系统。

== 逻辑表与约束

所有表使用 InnoDB 和 `utf8mb4`。实体主键使用自增 `BIGINT`，关系表使用组合主键。名称、编码和电话使用字符串，保留电话号码的前导字符。实体和可更新的配置记录包含创建和更新时间，分配关系记录创建时间。字段长度、可空性和索引定义见 link:../backend/src/main/resources/db/migration/V1__create_rbac0_schema.sql[Flyway 初始迁移]。

[cols="1,2,3",options="header"]
|===
|逻辑表 |关键字段 |约束与用途

|`organization` |组织 ID、编码、名称、类型、上级组织 ID、经理姓名、原表上级名称
|编码唯一。分公司无授权上级，部门必须填写上级。外键保证上级存在，导入和组织维护 Service 校验上级类型为公司。V2 保留原表上级名称，便于展示原表中的总公司与分公司关系。

|`employee` |员工 ID、用户名、姓名、所属组织 ID、原表字段
|员工 ID 为主键，用户名唯一，归属引用组织。待匹配记录允许空归属。

|`rbac_role` |角色 ID、角色名、所属组织 ID
|所属组织引用组织，空归属表示全局。同一组织范围内角色名唯一，全局角色名同样唯一。

|`business_system` |系统 ID、系统编码、名称、所属组织 ID
|系统 ID 为主键，系统编码唯一，所属组织为必填外键。

|`permission` |权限 ID、权限码、名称、系统 ID、定义所属组织 ID
|权限 ID 为主键。业务权限在同一系统内按权限码唯一，管理权限的权限码全局唯一。

|`employee_role` |员工 ID、角色 ID
|分别外键关联员工与角色，组合主键防止重复分配。

|`role_permission` |角色 ID、权限 ID
|分别外键关联角色与权限，组合主键防止重复授权。权限 ID 区分不同系统的同名动作。

|`organization_permission` |组织 ID、权限 ID、状态
|组合主键确保每个组织与权限组合只有一个配置。V5 扩展状态为 `OPEN`、`DISABLED`、`REOPENED`。组织级停用优先于角色授权。

|`organization_permission_regrant` |组织 ID、角色 ID、权限 ID
|三列为组合主键，引用组织权限策略和角色权限关联。角色权限关系删除时级联移除重授。

|`administrator_scope` |员工 ID、管理范围类型、组织 ID
|员工 ID 为主键。全局范围的组织 ID 为空，组织范围的组织 ID 必填。公司级或部门级由组织类型决定。

|`catalog_entry` |系统名、模块名、功能点、说明、五个角色的原表动作文本
|系统名、模块名、功能点组合唯一。各角色动作文本可空，供管理端对照原表展示。

|`login_account` |员工 ID、密码哈希
|员工 ID 同时作为主键和外键，V3 随登录模块增加。

|`simulated_request` |申请 ID、系统 ID、标题、状态
|系统 ID 为外键，一个系统有多条申请。V4 增加系统与 ID 索引，以及状态取值约束 `PENDING`、`APPROVED`。
|===

外键使用默认限制行为。仍被引用的实体删除时，Service 需按业务规则先处理关联。数据库保证引用存在、关系不重复和本行状态合法。部门上级类型、待匹配员工能否分配、管理员能否跨组织配置，以及停用生效，由对应 Service 校验。审批在授权通过后仅更新仍待审批的行。

== 审查与复现

* 员工通过工程部角色获得工程部系统的审批权限。公司系统即使也有同名权限码，仍使用另一权限 ID。
* 管理员撤权或离职时，已有员工角色和角色权限关系继续有效。组织停用某业务权限时，目标范围内所有有效角色路径均受停用规则约束。
* 公司管理员和部门管理员各持有一个管理范围。组织停用、重新开放及范围重授由超级管理员执行，规则见 link:组织权限停用与重新开放.md[组织权限停用与重新开放]。
* 运行 `python docs/design/build-chen-er.py` 可重建 StarUML 项目和 SVG。用 StarUML 打开 `docs/design/RBAC0-陈氏ER图.mdj` 可编辑图元。手工调整后，应同步更新生成脚本中的布局以保持预览一致。
* 数据库迁移验证目标为 Navicat 本地连接 `ooad_rbac` 下的 C1 库 `ooad_rbac0`。
* V1 SQL 独立验证了十张表、十项约束拒绝、同名权限隔离和事务回滚。接入 Maven 后，由 Flyway 在隔离空库执行 V1、V2，两条迁移历史均成功，JPA 映射通过校验。Flyway 11.7.2 对 MySQL 8.4 提示版本未经其测试，本项目已在 8.4.8 实测迁移及复跑。
