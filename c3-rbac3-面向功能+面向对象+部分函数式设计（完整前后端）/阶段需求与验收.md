## 一、输入与范围

输入为 C2 面向功能、面向对象两套可运行基线、共同契约和验收数据、[老师日期图](../项目整体方向规划和技术细节/老师的交付要求/检查日期和内容.png)、[项目开发规划](../项目整体方向规划和技术细节/RBAC_Development_Plan.md) 及 [技术规范](../项目整体方向规划和技术细节/RBAC_Technical_Conventions.md)。检查窗口为 12 月 22–24 日，20 分。日期图明确两种设计分别交付前后端、部分功能采用函数式设计。[检查内容文字](../项目整体方向规划和技术细节/老师的交付要求/检查内容.txt) 的详细步骤止于第二次检查。

两条开发线分别在对应 RBAC1 上新增约束管理、校验和授权联动，交付各自可运行的完整前后端。管理端涵盖基础分配、继承、约束管理和冲突反馈。业务模拟端继续分别展示授权和执行结果。若动态约束纳入验收，增加会话激活／切换角色界面与冲突反馈。

## 二、设计与交付

- 建议以角色互斥为首个约束。静态规则作用于角色分配，动态规则在会话激活时校验。每条规则需明确检查直接分配、继承可达或当前有效角色集合，以及修改继承边或规则后既有分配和会话的处理方式。
- 面向功能版使用可复用的约束计算步骤。面向对象版按 GRASP 将规则交给具有所需信息的领域对象或领域服务，由应用 Service 负责用例、事务和持久化端口。两条线的契约、规则和测试期望一致。
- 建议以角色互斥冲突检测体现函数式设计。纯函数以角色集合及规则为输入，返回冲突结果，由调用方负责数据库、会话和页面反馈。用设计说明及测试展示输入与结果。
- 归档两套可启动的后端、配套完整前端、更新的数据与两版 Service 设计、约束与函数式说明、两版测试报告、运行操作和演示材料。补齐老师的 C3 细则后确定部署方式及额外的图、报告和展示要求。

## 三、共同验收

| 编号 | 场景与预期 |
| --- | --- |
| C3-01 | 继承保留且无冲突时，员工可使用继承得到的权限执行操作 |
| C3-02 | 分配互斥角色被拒绝且无部分写入。若动态约束纳入范围，激活互斥组合也被拒绝，合法会话状态可继续使用 |
| C3-03 | 至少验证一条继承与约束的联动。建议用新增继承边令现有角色组合命中互斥的场景，按最终规则处理并验证关系、分配和会话状态 |
| C3-04 | 角色、继承或规则发生已确认会影响会话的变化时，同一会话下次受保护请求按最新规则判断 |
| C3-05 | 两版回归 C1 的分配、撤权和 C2 的传递继承、环路拒绝、组织策略联动与申请生命周期。同数据下的授权、错误和业务结果一致 |
| C3-06 | 两套完整前后端独立可启动，演示约束管理、冲突反馈、业务模拟与函数式功能 |

## 四、前置依赖与待确认项

先取得 C2 两套验收版本，确认第三次检查细则和约束覆盖范围。随后确定约束集合口径、继承变动后的处理策略、动态角色激活及 Redis 会话行为、函数式设计展示点和部署证据。静态／动态规则、继承覆盖及既有数据处理确认后，才能将 C3-02 至 C3-04 细化为可执行用例。
