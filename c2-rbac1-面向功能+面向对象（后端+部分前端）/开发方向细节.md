# C2 开发方向细节 · RBAC1

状态：双后端、继承规则、双路径入口、会话隔离和申请 CRUD 规则已确认。基线为 `0e8778e`。本地／集群分工已确认。参见 [阶段需求与验收](./阶段需求与验收.md)。

## 1. 开发线与共用资产

在 C2 目录并排布置 `backend-func/`、`backend-oo/`，分别可独立执行 Maven clean 构建和测试。保留同一个 C1 来源，记录基线提交和两版启动入口。C2 的 `api/openapi.yaml` 从 C1 契约扩展，示例数据、HTTP 契约测试输入和浏览器验收脚本使用同一份，两版各自保留单元测试和验收结果。部分前端拟从 C1 的管理端与业务模拟端扩展，落地形态见第 6 节。

数据库分别为 `ooad_rbac1_func`、`ooad_rbac1_oo`。两版共用 Redis 实例，使用不同的会话命名空间和 Cookie。延用 Java 21、Spring Boot、Maven、MySQL、Spring Data JPA、Flyway、Spring Security、Spring Session Redis、Vue 3 + TypeScript，以及 C1 的 CloneFactory Maven 注解处理链。原有接口、请求语义和业务错误保持兼容，删除角色时新增继承引用冲突这一条件。

## 2. 模块与契约

| 模块 | 拟实施范围 |
| --- | --- |
| 继承维护 | 拟用 `GET /api/roles/{roleId}/parents` 和 `PUT`／`DELETE /api/roles/{roleId}/parents/{parentRoleId}`，沿用项目接口草案。路径中的 `roleId` 是接收权限的高级角色，`parentRoleId` 是提供权限的低级角色。页面用「继承自」展示该方向；查询列出直接边 |
| 员工有效权限 | 拟用 `GET /api/employees/{employeeId}/effective-permissions`，按指定业务系统查询该员工当前可用动作。后端在返回前检查管理员对员工和目标系统的可见范围，再按目标员工的系统准入与组织策略计算。按权限 ID 去重，使用稳定排序和约定分页，角色的直接权限继续用 C1 查询 |
| 业务授权与模拟 | 保留 C1 审批入口和统一实时判权，新增申请发起、详情、修改、撤回、驳回和删除。各写入依据服务端确定的系统、动作、操作者及当前申请状态检查，见第 6.3 节 |
| 组织权限 | 保留现有停用、重开、重授端点及直接角色—权限绑定。扩展候选来源角色的查找，保留停用优先级与 C1 的全局管理员规则 |

用 C1 的 DTO／VO、整数 ID、字段校验、Cookie 和 CSRF 方式。契约定稿时写明权限、分页、成功例和业务错误。拟沿用 401、403、404、409 的分类，新增环路和自继承冲突用例，标明归属不符与需要先解除继承引用的错误。合法重复 PUT／DELETE 幂等。保留共用 YAML 为主契约，按项目规范校验并生成 UTF-8 JSON，再按授权范围处理 Apifox。

## 3. 继承边界、数据与事务

先区分员工分配、角色继承、权限授予三种关系。例子中，员工小林只分配了工程部「主管」。若工程部「主管」继承工程部「审批员」，而「审批员」直接拥有报销审批权限，小林便能通过继承取得该权限。只分配「审批员」的员工仍只拥有该角色及其继承来源的权限。若「主管」还继承「审计员」，两个来源权限取并集，重复权限只列一次。「高级／低级」描述这一条边上的接收方和提供方，角色无需额外维护全局等级，组织层级也不自动生成角色继承。

| 候选关系 | 推荐结果 | 原因 |
| --- | --- | --- |
| 工程部主管 → 工程部审批员 | 允许 | 角色归属同一部门，操作者仍须有管理权 |
| 公司主管 → 公司审批员 | 允许 | 两端都归属同一公司 |
| 工程部主管 → 财务部审批员 | 拒绝 | 两端归属不同部门，避免修改一条边时扩散到其他组织 |
| 工程部主管 → 公司审批员 | 拒绝 | 公司和部门有上下级关系，但仍是不同角色归属 |
| 共享主管 → 共享审批员 | 由全局管理员维护 | 两端均无组织归属，仍需走目标系统和组织策略判权 |
| 工程部主管 → 共享审批员 | 拒绝 | 组织自有角色与共享角色归属不同 |

同归属规则约束的是**角色之间**的连边。谁能管理角色、角色可以分配给哪些员工，继续按 C1 的规则检查。公司管理员可以管理授权范围内的下属部门角色，仍可在该部门内维护合法继承。若从一开始允许跨归属，须额外规定方向、审批主体以及如何核算受影响的成员。建议本阶段用同归属图讲清 RBAC1，跨归属留到出现实际业务用例时再单独设计。

沿用同一例子，假设小林有报销系统准入，且其主管只能经审批员取得报销审批权限。

| 变化 | 小林下一次审批 |
| --- | --- |
| 继承边存在，适用范围没有该动作的停用或重开限制 | 可审批 |
| 工程部或其他适用组织停用该动作 | 拒绝，继承关系保留 |
| 适用组织重新开放，还未重授审批员 | 仍拒绝 |
| 公司和工程部均处于重开状态，两个范围都重授给审批员 | 可审批；只完成一处重授时仍拒绝 |
| 删除主管到审批员的唯一授权路径 | 拒绝；如果还有一条合格路径则继续允许 |
| 合法重连，审批员原有重授仍有效 | 恢复；如果审批员的直接权限曾被撤销，则重新授予该权限后仍需按适用范围显式重授 |

重授绑定直接持有权限的「审批员」。C1 的重授记录以角色与直接权限关联为外键，可继续使用已有接口和清理规则。若主管还能到达另一个同样持有审批权限的角色，公司重授给审批员、工程部重授给另一个角色时，两个来源各自都缺一个范围，审批拒绝。

- **存储与遍历。** Flyway 在 C1 V1–V5 后追加迁移。拟新增 `role_inheritance`，列为 `senior_role_id`、`junior_role_id`，组合键防重复，两个外键引用角色，补逆向索引和自继承检查约束。加边前从低级角色沿出边遍历，若能到达高级角色则拒绝。两版用访问集合处理多路径和传递关系。角色删除前先解除所有入边与出边。
- **管理范围。** 两端角色须同归属且都在操作者管理范围内，共享图由全局管理员维护。继承会影响高级角色及所有能到达该角色的角色。新增边时评估这些角色与现有成员因为继承新增的权限来源，按 C1 规则检查权限归属、目标员工范围、组织开放或重授条件以及停用冲突。给继承角色分配员工、给被继承角色新增直接权限时做对应正向／逆向展开，避免换一个写入入口即可绕过检查。
- **实时授权。** 按 C1 先查可信身份与目标系统准入，然后读取适用组织策略。权限按目标系统解析；系统归属及其上级适用，非全局管理员另计员工归属及其上级。任一适用范围停用即拒绝，随后沿用全局管理员默认业务能力。对于普通员工，展开当前直接角色，找到直接持有目标权限的所有可达来源角色；在 `REOPENED` 时逐个来源校验其是否同时满足所有适用重授范围，至少一个合格才允许。例如主管继承审批员，审批权限直接挂在审批员，则重授审批员。删边只移除路径，合法重连后可复用仍有效的来源重授。保留 C1 再次停用及撤销直接角色权限时的重授清理语义。
- **并发与一致性。** 首版建议用 JPA 悲观写锁锁定预置的数据库锁记录，先取锁，再以读已提交读取当前关系并校验、写入。同一把锁覆盖继承增删、角色删除及依赖继承图做范围检查的两类分配写入，之后沿用 C1 的实体和权限锁顺序，避免各实例分别通过环路校验或漏掉并发产生的继承来源。适用组织策略写入与分配写入沿用 C1 权限行串行化。判权读取同一次请求中的一致数据库视图；关系提交后，下一次请求重新读取 MySQL。Redis 按 C1 保管登录会话。

## 5. 双线维护与阶段末模型比较

贫血／充血／满血设计对照列为阶段末待办。待 C2 核心功能、前端和共同验收基本完成后，以实际代码为依据，用「给工程部主管新增继承来源审批员」比较三种模型，覆盖合法新增、重复提交、自继承和间接环路。结构化与 DDD 的差异及 GRASP 随两套核心后端开发同步准备。下表记录阶段末比较方向。

| 对照项 | 偏贫血 · 面向功能版 | 充血 · 面向对象版 | 满血 · 扩展示例 |
| --- | --- | --- | --- |
| 状态载体 | 角色关系记录和邻接关系 | 持有关系与规则的角色层级领域对象 | 负责发起本用例协作的角色层级对象 |
| 谁判断成环、何时修改 | 继承 Service 按过程遍历、校验，随后保存 | 领域对象用现有关系判断并完成合法状态转换 | 领域对象发起加载、校验和写入协作，提交仍由外层事务控制 |
| 谁访问数据 | Service 经 JPA Repository | 应用 Service 调用端口加载和保存，JPA 由适配器处理 | 对象通过注入的窄端口协作，小样使用内存实现 |
| 维护取舍 | 流程直观，多个入口容易重复规则 | 规则能独立验证，需维护领域与持久化映射 | 领域对象掌控更多步骤，测试需替换端口，持久化时机和依赖需要重点解释 |

满血在这里是**本项目用于对照的一种定义**，指领域对象还主导用例中的外部协作；若教师有明确定义，按课程定义调整展示。两套正式后端分别提供偏贫血和充血实例。进入阶段末待办后，先完成满血的类图、时序图和职责说明，再视进度补独立可运行的小样，验证同组输入与预期。示例没有第三套 Web 服务、数据库或部署栈。贫血与富行为领域模型的参考见 [Anemic Domain Model](https://martinfowler.com/bliki/AnemicDomainModel.html)。

| 维护对象 | 维护方式 |
| --- | --- |
| 共同业务约定 | OpenAPI、场景编号、错误码、测试数据和 HTTP 断言只维护一份。测试用相同数据分别跑两套服务，安装和运行入口各自保留 |
| 各自实现 | 分别维护继承、授权和分配用例，评审同时看两版行为和职责落点；C1 登录、会话、工作区等稳定实现沿用各自基线，避免为共享代码引入额外运行耦合 |
| 数据变更 | 两库保持相同的可观测业务约束；本阶段建议使用相同逻辑表和迁移版本。迁移变更同时核对两边并跑空库安装、C1 原库升级及数据验证 |
| 后续修复 | 先判定是否改变共同业务规则。共同缺陷先增加会失败的共同场景，再修两版；仅一边有实现缺陷时补该版回归，并用共同场景核对对外行为 |
| 交付与分支 | C2 在同仓库留存各版构建入口、配置、测试记录及代码索引，各自作为 C3 的来源。Git 提交和推送按用户授权执行，提交说明用简洁中文 |

## 6. 前端、完整 Excel 与业务系统验收

### 6.1 一套前端连接两套后端

课程环境发布一个前端站点及一份 Vue 构建产物。同一站点首页提供「面向功能版」「面向对象版」，两者加载同一套组件与页面，URL 前缀固定本次访问的版本。页面顶部显示当前版本，切换按钮导航到目标版本入口，浏览器也可以同时打开两个入口逐项对照。

| 浏览器入口 | 对应 API | 网关转发目标 |
| --- | --- | --- |
| `/func/` | `/func/api/...` | 面向功能后端的 `/api/...` |
| `/oo/` | `/oo/api/...` | 面向对象后端的 `/api/...` |

登录、读取会话、领取 CSRF、业务写入及退出都使用当前版本的 API 前缀。网关按固定规则去掉版本前缀，两个后端仍实现相同的 OpenAPI 路径。深链、登录后的默认工作区和系统切换都保留版本前缀，API 请求先匹配代理，页面刷新才使用 SPA 回退。浏览器只访问同源地址。入口不能切换成任意后端地址，单个后端不可用时页面显示该版错误并保留版本选择。参考 [Nginx 反向代理 URI 规则](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)。

两版 Redis 连接指向同一个实例。建议部署配置采用以下命名和 Cookie 路径。

| 后端 | MySQL 库 | Redis 会话命名空间 | Cookie 名 | Cookie Path |
| --- | --- | --- | --- | --- |
| 面向功能 | `ooad_rbac1_func` | `rbac1:func:session` | `RBAC1_FUNC_SESSION` | `/func/` |
| 面向对象 | `ooad_rbac1_oo` | `rbac1:oo:session` | `RBAC1_OO_SESSION` | `/oo/` |

切换通过页面导航重新读取目标版会话、员工身份与工作区，已在该版登录则继续使用其会话，否则进入该版登录页。同一浏览器可在两个标签页分别用不同账号登入两版。两库以同一原表和演示数据初始化，后续独立写入。在功能版修改角色、申请或权限只写功能版 MySQL，面向对象版保留自身数据。登录、会话校验与退出均使用本版命名空间。业务导航与版本切换是两个独立操作。部署时保留两套后端服务。若课程入口无法按路径路由，两版可各用一个子域名并继续复用同一前端镜像。参考 [HTTP Cookie 作用范围](https://www.rfc-editor.org/rfc/rfc6265.html#section-4.1.2.4)。

### 6.2 三份 Excel 完整交付

- 复用 C1 的 `--import-excel`，将同一批课程工作簿导入两版数据库，由两版前端分别展示全部员工、部门与应用软件功能权限清单。按 C1 本地基线核对原表员工 10,000 条、部门／组织目录 111 条、权限清单 359 条。这些数量按原表来源统计，合成演示行单独核对。
- 复验逐页字段、层级和空值，保留 C1 电话脱敏、54 条员工组织待匹配标记、合并列展开及空动作处理。管理员视图继续按其组织范围过滤。用全局管理员验收整表，另用局部管理员验证隔离。原表权限清单供核对，演示授权使用独立初始化的合成账号、角色、权限和申请。
- 当前按用户提供的原表导入两库并做本机全量验收，保留 C1 的页面电话脱敏。课程集群由队友通过只读输入导入，具体表版本在交接时确认。源工作簿沿用本地忽略规则，代码仓库与镜像交付导入工具、目录约定及验证结果。全量脱敏副本指保留全部数据行、列结构、层级及关联，以一致的替代值处理个人标识，例如姓名、用户名和电话。当前采用原表录入口径。参见 [课程原表说明](../excel/README.md) 和 [C1 全量验收记录](<../c1-框架-rbac0-结构化+面向功能/docs/本地验收记录.md>)。

### 6.3 公司与部门系统的申请 CRUD

在甲公司、工程部、财务部的可操作演示系统使用统一申请生命周期，由系统归属和权限配置决定可见工作区与操作。工程部承担继承加边／删边的审批验收，乙公司作为跨公司隔离对照。各版准备申请人、审批人和管理员的合成账号，补齐所属系统的权限和可复现数据。

C1 已提供按系统分页的申请列表和审批，现有记录只有 `PENDING`、`APPROVED`。C2 保留这两种状态和原审批 API，追加 `WITHDRAWN`、`REJECTED`。下表记录已确认的状态与操作主体，API 路径作为共同 OpenAPI 的输入。

| 动作 | 拟用 API | 状态与操作权限 |
| --- | --- | --- |
| 查询列表／详情 | `GET /api/business-systems/{systemCode}/requests`、`GET /api/requests/{requestId}` | 延续 C1 的系统准入和分页，按记录所属系统鉴权；列表和详情仅返回未删除记录 |
| 发起 | `POST /api/business-systems/{systemCode}/requests` | 拥有目标系统发起权限的员工可创建 `PENDING` 申请。服务端从当前会话记录申请人 |
| 修改 | `PATCH /api/requests/{requestId}` | 申请人可修改自己的 `PENDING` 申请，修改标题等业务字段后仍为 `PENDING` |
| 撤回 | `POST /api/requests/{requestId}/withdraw` | 申请人可将自己的 `PENDING` 申请变为 `WITHDRAWN`。原单保留且不可重新提交 |
| 审批通过 | `POST /api/requests/{requestId}/approve` | 拥有该系统审批权限的员工可将 `PENDING` 改为 `APPROVED` |
| 驳回 | `POST /api/requests/{requestId}/reject` | 拥有该系统驳回权限的员工可将 `PENDING` 改为 `REJECTED` |
| 删除 | `DELETE /api/requests/{requestId}` | 申请人可逻辑删除自己处于 `REJECTED` 的申请。列表与详情隐藏原单，保留驳回状态和日志 |

- **授权。** 目标系统来自系统路径或持久化申请，操作者来自服务端会话。拟按系统为发起、修改、撤回、审批、驳回及删除配置动作权限，接入统一实时授权，叠加申请人检查及状态校验。请求体只接收可修改业务字段。审批仍复用 C1 权限码与已审批冲突行为。
- **迁移与并发。** 在 C1 迁移之后追加申请人、状态与删除标记相关迁移。C1 历史申请没有申请人，保留原有可查询和按系统审批能力，申请人专属动作须有明确归属。通过同事务锁定或条件更新校验当前状态，审批、驳回、撤回竞争同一待审批申请时只允许一个状态转换提交。修改与状态变更并发时按实际提交顺序核查。状态冲突按共同契约返回 409，越权按既有规则返回拒绝。
- **可追踪日志。** 两版沿用 Logback 和现有入口日志，为列表、详情及各写动作补充可在 Swarm 定位的操作结果。日志记录版本、动作、系统、申请 ID（列表可省略）、操作者标识、鉴权或执行结果及失败业务码。写动作成功只在事务提交后记录，权限拒绝和状态冲突可单独定位。日志保留删除动作，省略申请内容、凭据、Cookie 和 CSRF 令牌。
- **页面。** 系统页提供发起、列表、状态、详情和各动作入口。页面按状态、本人身份和权限展示可用动作，服务端执行最终校验。每轮准备多条独立申请，分别走通过、撤回及驳回后删除三条路径。刷新和重新登录后核对实际存储状态，验证失败请求不会修改记录。

`WITHDRAWN` 是终态。页面保留已撤回记录，服务端拒绝其修改、再次提交和其他状态转换。如需继续办理，申请人可新建申请。申请人在待审批时可直接修改内容。课程集群实际用表随部署交接确认。

## 7. 实施顺序、测试代码与验收

### 7.1 实施顺序

1. **设计与契约。** 按已确认的继承、申请规则和前端入口完成数据设计、共同 OpenAPI 和页面交互，锁定错误码、分页和同一组测试数据。将 C2-01 至 C2-14 关联到契约、自动化测试和页面，同时确定关键 API 的证据清单。
2. **两版基线。** 两版各从 C1 建立可运行基线，先跑 C1 回归。保留 Java 21、显式类型、中文 Javadoc、CloneFactory 和 Maven 注解处理器。代码文件开头说明职责及关联，关键规则用简短注释，权限或派生字段显式映射。
3. **实现与持续测试。** 先用有限场景观察预期失败，再依次实现图校验、权限展开、组织联动、申请 CRUD 和前端。图规则跑直接、传递、多路径、自继承和环路单测；真实 MySQL / Redis 验证并发成环、事务回滚、Flyway、重授、申请状态竞争及同一会话撤权。两套后端执行 Maven clean 验证和 CloneFactory 生成检查，前端做类型检查、生产构建及两版浏览器回归。
4. **设计复核与答辩。** 以实际代码回填两版包图及抽查 API 的类图、时序图，关联需求、测试、页面、关键方法和日志。补充结构化与 DDD 对照、GRASP 说明和 JavaEE 技术清单。三种模型比较安排在 C2 核心功能与验收基本完成后。建议先固化新增继承材料，随后完善权限查询和审批两条链。
5. **课程交接。** 本地用 Docker Desktop 和 Compose 验证两套实现。最后交付队友可执行的 Swarm 操作说明和部署配置，以及本地验证结果、已完成功能、未完成目标和优化方向。课程集群部署和现场验收由队友执行。

### 7.2 测试代码编写计划

每个模块在共同契约和验收预期明确后先编写对应测试，观察新行为缺失时的预期失败，再实现并通过回归。C2 后期用实际测试代码对两套后端及前端执行集中验收。暂按 C1 的 Maven、JUnit、JaCoCo 和 Playwright 组织，老师提供的测试 skill 下载后先阅读，再补齐测试工程布局、命名、工具与报告口径。

| 代码层次 | 编写与维护 | 用例重点 |
| --- | --- | --- |
| 两版各自的单元测试 | 面向功能版测处理函数或 Service，面向对象版测角色层级和申请状态规则。用相同的规则样例比较预期 | C2-01 至 C2-05、C2-12、C2-13。直接与传递继承、多路径、自继承、环路、非法状态转换 |

| 两版 MySQL／Redis 集成测试 | 使用隔离测试库、独立测试会话命名空间和可重复初始化的合成数据。验证 Flyway 升级、JPA 保存、并发事务和会话读写 | C2-03、C2-04、C2-06 至 C2-08、C2-10、C2-13、C2-14。并发成环、唯一合法转换、失败不写入、提交后的日志结果 |

### 7.3 后期执行与测试交付

- 两版各执行 Maven 验证与完整 C1 回归，再针对两版运行共同 HTTP 用例、真实依赖集成用例和前端端到端用例。失败时按需求编号定位到接口、代码和测试。正式验收记录未执行或跳过的项目及原因。
- 交付可运行的测试代码、命令、测试配置示例、合成测试数据说明和需求追踪表。归档两版的执行结果、通过／失败／跳过数和覆盖率。报告记录测试的版本、环境和失败场景。真实工作簿沿用既有提供方式。
- 测试追踪至少包含「需求编号 → API 或页面入口 → 测试代码 → 输入和断言 → 两版执行结果」。抽查接口再关联类图和时序图，教师可以从任一入口复查。课程测试 skill 到位后，按其要求调整组织与验收口径。
