## 一、输入与范围

输入为可复现的 C1 基线、共同 OpenAPI、演示数据、C1 验收用例、[老师日期图](../项目整体方向规划和技术细节/老师的交付要求/检查日期和内容.png)、[检查细则](../项目整体方向规划和技术细节/老师的交付要求/检查内容.txt)、[开发规划](../项目整体方向规划和技术细节/RBAC_Development_Plan.md) 和 [UML skill](../项目整体方向规划和技术细节/老师提供的skill/uml-class-sequence-diagrams.zip)。检查窗口为 11 月 24–26 日，30 分。

从同一 C1 版本分别交付面向功能和面向对象的 RBAC1 后端。新增继承关系查看、添加、删除和有效权限查看，支持直接与传递继承、权限去重，拒绝自继承和环路。两套后端按同一契约和数据验收，保留 C1 授权入口。部分前端建议优先实现继承维护、有效权限查看与业务模拟验证，能分别连通两版。

## 二、设计与交付

- 建议在契约中明确“高级角色继承低级角色”以及边的字段方向。有效权限由直接角色及其可达继承角色的权限并集计算。Service 职责分为员工与角色分配、角色继承管理和授权。新增边前验证环路，写入和校验共享一致的事务边界。
- 面向功能版按读取、校验、保存、遍历和判权组织过程，用模块结构图与流程图说明调用和数据传递。面向对象版由应用 Service 协调用例与事务，角色层级领域模型或领域服务负责维护不变量与继承展开，持久化经领域仓储端口及 Infrastructure JPA 适配器。以新增继承等用例说明信息专家、控制器、高内聚和低耦合如何落到职责与代码。
- 以新增角色继承对照偏贫血和充血的责任分配，以及满血模型下领域对象承担的行为和依赖。老师现有文件未规定满血交付形态，当前仅将同用例设计对照列为建议。
- 交付两套后端、可联调的部分前端、继承表及迁移设计、Service 与 GRASP 说明、模型比较、模块图和流程图、后端包图、选定 API 对应的类图、时序图与代码定位。类图和时序图按教师 UML skill 以代码为准，生成 PNG 与 SVG，并检查 Service 布局、连线、执行条、分支和异常路径。
- 助教检查时在 Docker Swarm 中部署前端、后端与数据库，展示页面请求产生的 Logback 日志。按项目技术栈提供 Redis 会话依赖和启动、操作说明。教师检查时用需求、测试和前端相互对照，准备结构化与 DDD 差异、GRASP 示例及所用 JavaEE 技术。

## 三、共同验收

| 编号 | 场景与预期 |
| --- | --- |
| C2-01 | 员工的直接角色经一条边或多条边获得权限，有效权限可查，模拟业务获准 |
| C2-02 | 多条路径指向同一权限，列表仅显示一次，授权通过 |
| C2-03 | 添加自继承或形成直接、间接环路的边时拒绝，原图保持完整 |
| C2-04 | 删除唯一继承路径后，同一会话下一次请求被拒绝。另一条有效路径存在时仍获准 |
| C2-05 | 两版同数据运行共同契约和 C1 回归，成功、拒绝、错误码及状态一致 |
| C2-06 | 分别用前端联调两套后端，在 Swarm 检查前后端和数据库服务，操作与对应 Logback 日志可复查 |
