## 一、已确定的范围

- 从 C1 GitHub `main` 的已交付提交 `0e8778e` 派生面向功能与面向对象两套 RBAC1 后端，数据库分别为 `ooad_rbac1_func`、`ooad_rbac1_oo`。两版共用一份 OpenAPI、同一组验收数据和场景，保留 C1 的登录、Redis 会话、工作区切换、组织范围和审批入口。C1 验收记录包含 35 组 HTTP 方法与路径、30 项后端测试、管理端与业务模拟端的浏览器验收。见 [C1 OpenAPI](<../c1-框架-rbac0-结构化+面向功能/api/openapi.yaml>) 和 [C1 本地验收记录](<../c1-框架-rbac0-结构化+面向功能/docs/本地验收记录.md>)。
- 支持查看、添加、删除直接继承边，展开直接与传递继承并查询员工有效权限。同一权限可来自多条路径，查询结果按权限 ID 去重。自继承、直接与间接环路均拒绝。有效权限查询与审批使用相同的实时授权规则。
- 沿用 MySQL、Flyway、Spring Data JPA、Spring Security、Redis 会话、统一实时授权入口、C1 CloneFactory 和 Maven 注解处理器。RBAC3 的角色互斥、角色激活等约束归入 C3。技术与阶段依据见 [项目技术规范](../项目整体方向规划和技术细节/RBAC_Technical_Conventions.md) 和 [分阶段开发规划](../项目整体方向规划和技术细节/RBAC_Development_Plan.md)。

- C2 前端提供三份 Excel 的完整数据浏览，保留既有导入和组织范围规则。公司与部门业务系统提供测试账号、权限和申请，页面可查询、发起、修改未审批申请、撤回未审批申请、审批、驳回和删除已驳回申请。各动作纳入 Logback 记录。

## 三、共同验收场景

同一测试数据和预期分别在两版执行。审批使用普通员工的原会话及新的待审批申请，验证拒绝后申请仍待审批，避免把重复审批的 409 当成撤权结果。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| C2-01 | 普通员工直接分配给主管；主管继承审批员，另有两跳传递链 | 角色详情显示直接继承边；指定系统的员工有效权限包含审批；原审批入口允许操作 |
| C2-02 | 两条路径获得同一审批权限；另一系统也有同名权限码 | 同一权限 ID 只显示一次；权限按目标系统区分。没有目标系统准入时仍拒绝 |
| C2-03 | 尝试自继承、反向边、闭合长链；并发提交两条各自合法、合并后成环的边 | 非法请求返回约定冲突；原有合法边保持完整；并发请求最多一条提交，最终图无环 |
| C2-04 | 同一会话先通过审批；删除唯一继承路径后审批另一条待处理申请。另测删边后仍有有效路径 | 唯一路径删除提交后下一次请求返回 403，申请仍待审批；有替代有效路径时继续允许 |
| C2-05 | 检验不同归属角色、共享角色、越权维护／查询、重复增删和删除被引用角色 | 跨归属边拒绝，局部管理员不能维护共享边或越权查询。合法的重复增删幂等。有继承边的角色删除返回 409 |
| C2-06 | 组织停用、重开、分范围重授叠加多个继承来源 | 停用优先，含全局管理员适用范围。重开后按 C1 规则恢复全局管理员；普通员工须能到达某个在所有适用重开范围均获重授的权限来源角色。不同来源的重授不能拼接；删除继承边后重连可复用仍有效的来源重授，删除直接授予则清理其重授 |
| C2-07 | 加入继承边、给已被继承的角色新增权限，或给新员工分配已有继承的角色 | 按 C1 的分配范围与停用规则评估继承影响。越权或停用冲突时事务不写入，合法分配可立即生效 |
| C2-08 | 使用共同契约验证两版，分别回归 C1，部分前端分别与两版联调，由队友在课程 Swarm 集群验收 | 两版响应、状态和业务结果一致；C1 登录、退出、工作区、分配、组织策略与审批回归通过；可定位页面操作与 Logback 日志 |
| C2-09 | 两版导入并浏览完整课程 Excel，按原表来源与演示数据分别核对 | 全局管理员可分页核对原表全部记录，当前基线为 10,000 名员工、111 条组织目录和 359 条权限清单。局部管理员按 C1 规则只看到其范围内数据 |
| C2-10 | 同一浏览器的两个标签页分别通过 `/func/`、`/oo/` 以不同账号登录，在其中一版审批并退出 | 请求进入 URL 指定的后端。共用 Redis 实例时，两版仍各有独立登录身份和 CSRF。关闭一版会话不影响另一版，审批结果和角色配置仅写入当前版 MySQL 库 |
| C2-11 | 使用合成员工操作公司及部门系统，验证成功、继承撤权与越权拒绝 | 可从工作区进入对应系统，完成申请 CRUD 及通过、撤回、驳回场景。鉴权失败的申请保持原状态，访问非授权组织系统受限 |
| C2-12 | 申请人发起并修改自己的待审批申请，再执行撤回。尝试编辑他人申请及重提撤回单 | 修改后仍待审批。撤回后保留为已撤回，拒绝修改和重新提交原单。越权或冲突请求不写入 |
| C2-13 | 驳回待审批申请后删除；并发提交审批、驳回或撤回 | 只有申请人可删除本人已驳回的记录，删除后从列表和详情中消失。竞争同一申请时只提交一次状态转换 |
| C2-14 | 完成每类申请操作，另触发授权拒绝与状态冲突 | 两版均可定位相应 Logback 日志。成功与失败结果对应实际提交状态，删除动作可追查 |
| C2-15 | 同系统缺少查看权、跨系统同码、只读查看全部状态、继承查看权和原会话撤权 | 列表与详情无 `request:read` 时为 403，已有申请写入还需查看权。只读可查但不能写，跨系统不通用。撤权后下一次读取拒绝，页面清空旧列表和详情 |
| C2-16 | 对象版申请应用服务、领域规则和持久化边界 | 应用服务只依赖申请仓储、系统查询和授权端口。纯领域对象管理状态，JPA 适配器保存并保留事务锁、日志及兼容响应 |

两版已完成本地浏览器联调，各通过 11 项共同用例，并通过同一浏览器双标签页的登录、审批写入及退出隔离用例。各项结果与设计差异见 [双版本测试记录](测试/历史/双版本测试记录.md)。课程 Swarm 由队友在课程集群部署和验证。

## 四、已确认事项与后续工作

- 两套后端同仓库独立维护。高级角色继承同归属的低级角色，共享图由全局管理员维护。组织停用优先，重授绑定直接持有权限的来源角色，符合条件的合法重连可复用有效重授。
- 一套前端使用 `/func/` 与 `/oo/`，两个标签页可用不同账号登入。两版共用 Redis 实例，命名空间与 Cookie 独立，业务数据写入各自的 MySQL 库。
- 本机按用户提供的三份 Excel 原表全量录入，课程集群用表随部署交接确定。采用 Docker Desktop 和 Compose 开发测试，由队友部署课程 Swarm，阶段交付部署、校验、更新回退及排障说明。
- 贫血／充血／满血设计对照已交付，见 [比较材料](./三模型比较/README.md)。结构化、DDD 与 GRASP 已有实际代码及图件证据，GRASP 专项整理已完成，见 [grasp与项目](./grasp与项目.md)。
- 申请 CRUD 和操作日志纳入 C2。申请人可修改或撤回本人的待审批单，仅可删除本人的已驳回单。审批和驳回由拥有对应系统权限的账号执行。已撤回单不可再修改或重提。详见开发方案第 6.3 节。
