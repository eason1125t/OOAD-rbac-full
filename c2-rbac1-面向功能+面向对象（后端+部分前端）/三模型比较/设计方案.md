# C2 三种模型设计与比较方案

日期：2026-11-19。状态：用户已确认并完成实现及验证。设计、比较结果、小样和图件集中于本目录，测试仍位于统一测试目录。对应收尾第 3 项；正式后端和公共契约保持现状。本方案以已实现代码为证据，避免为展示模型而给正式系统继续增加接口和层次。

## 1. 推荐路线

采用“一个主用例、两套真实实现、一个隔离小样”：

- 主用例：给工程部主管新增“继承自审批员”的直接继承边。
- 功能版：跟读现有 Service 和静态规则，展示偏贫血／过程式组织。
- 对象版：跟读现有 RoleHierarchy，展示规则与关系数据的封装；不将尚在 Service 中的规则虚写为已经全部下沉。
- 满血：单独制作可运行的 Java 内存小样，展示领域对象如何主导加载、判断和保存的协作。它不是第三套可部署后端。
- 补充例子：用申请状态转换说明“把规则放进对象”带来的实际变化，避免仅凭角色图算法所在类名区分模型。

推荐总交付为一份比较说明、三组类图和时序图对照（复用现有四张，新增满血两张）、一个满血小样与测试记录。现有 42 张图继续作为真实实现依据，不重复另建正式后端。

## 2. 术语先明确

本项目按“业务行为在哪里、谁协调外部协作”比较，不按接口数量、类数量、代码行数或继承层数评分。

| 名称 | 本方案的工作定义 | 应避免的误解 |
| --- | --- | --- |
| 偏贫血／过程式 | 数据载体保存状态，主要业务步骤由 Service 和独立规则函数组织 | 不能说 func 的每一个对象都只有 getter/setter，也不能把所有结构化设计都判为错误 |
| 充血／富行为领域模型 | 领域对象持有业务数据及规则，应用服务负责用例、事务与端口协作 | 保留 Service、Repository 或基础设施适配器不妨碍领域对象有行为 |
| 满血（本项目对照定义） | 除维护规则和数据外，领域对象通过窄端口主动协调本用例的装载与保存；事务仍由外层界定 | 不作为通用、统一的架构等级；不等同直接使用 JDBC、不等同 Active Record，也不预设优于充血 |

Fowler 的 [Anemic Domain Model](https://martinfowler.com/bliki/AnemicDomainModel.html) 将缺少行为的数据对象与规则外置作为贫血模型特征，同时明确领域行为和持久化分层可以共存。[Domain Model](https://martinfowler.com/eaaCatalog/domainModel.html) 强调数据和行为结合；[Service Layer](https://martinfowler.com/eaaCatalog/serviceLayer.html) 解释用例边界和事务协作。这些参考支持贫血与富行为的区分，不提供本项目“满血”工作定义；若老师另有定义，先调整定义和展示方案。

## 3. 共同主线与不可改变的规则

用现有 `PUT /api/roles/{roleId}/parents/{parentRoleId}` 对照。roleId 是权限接收方 senior，parentRoleId 是提供方 junior。例子为工程主管 → 工程审批员；权限沿该方向取得，不由组织上下级自动生成。

正式两版保持相同顺序和边界：管理员资格 → 图写锁 → 读取角色 → 双端管理范围 → 同归属 → 自继承 → 既存边幂等 → 环路 → 增量授权影响 → 写入及事务提交。删除另有已实现的提前返回分支，本次图件主线聚焦新增。

以下要求用于核对真实两版，不因比较模型而调整：

- 共享图只允许全局管理员维护；跨归属与越权分别按契约拒绝。
- 从 junior 检查能否到达 senior；已有同向传递路径上加直达边合法。
- 继承写入先取全局图锁后读取关系，保持已有 READ_COMMITTED 和分配写入的协作锁。
- 新增来源影响 senior 及上游依赖角色，复用 AssignmentService 的影响范围和授予资格校验。
- 组织停用优先；员工最终授权的同源重授与“是否允许授予”是不同检查。
- 不缓存跨请求权限，删掉唯一有效路径提交后，原会话下一次请求拒绝；有替代路径时继续允许。

## 4. 三种模型的职责设计

### A. 功能版：以业务步骤组织

现有代码：[RoleInheritanceService](../backend-func/src/main/java/rolepermission/RoleInheritanceService.java)、[RoleInheritanceGraph](../backend-func/src/main/java/rolepermission/RoleInheritanceGraph.java)、[RoleInheritanceRules](../backend-func/src/main/java/rolepermission/RoleInheritanceRules.java)。

Service 控制完整流程、事务和写入；Graph 保存关系并委托静态规则；Rules 对显式邻接表做可达性、逆向影响及查环。不要为了让它看起来“更贫血”而删除已存在的良好封装。

调用顺序：Controller → Service → 管理资格／图锁／角色读取 → Graph → Rules → AssignmentService → Store.add → 提交。

优点是过程直观、容易跟读；主要取舍是规则能否被多个入口正确复用、流程增长后 Service 的可读性。它已有静态纯计算，不将其描述为“完全不能独立测试”。

### B. 对象版：规则和关系共同封装

现有代码：[RoleHierarchy](../backend-oo/src/main/java/rolepermission/domain/RoleHierarchy.java)、[RoleInheritanceService](../backend-oo/src/main/java/rolepermission/RoleInheritanceService.java)、[RoleInheritanceStore](../backend-oo/src/main/java/rolepermission/RoleInheritanceStore.java)。

RoleHierarchy 持有不可变关系快照，负责 inheritedRoles、dependingRoles、wouldFormCycle；应用 Service 仍控制管理范围、事务、增量授予检查和端口保存。

调用顺序：Controller → Service → Store.lockWrites/snapshot → RoleHierarchy.wouldFormCycle → AssignmentService → Store.add → 提交。

重要事实：当前 RoleHierarchy 负责计算，**不负责修改自身状态或保存继承边**。本方案不为使图更漂亮而新增一个未被业务使用的 add 方法，也不把现有 Service/JPA 模块全部改造成 DDD。

补充对照：[func 的 applyChange](../backend-func/src/main/java/simulation/BusinessRequestService.java) 与 [oo 的 BusinessRequest](../backend-oo/src/main/java/simulation/domain/BusinessRequest.java)。前者由 Service 检查并设置状态，后者在 rename/withdraw/approve/reject/delete 中维护状态和申请人边界。此例更直接说明富行为对象的价值。

### C. 满血小样：领域对象主导本用例协作

以下为已按方案实现的小样类型，源码位于本目录，不属于两套正式后端：

| 小样类型 | 责任与限制 |
| --- | --- |
| FullRoleHierarchy | 每次用例创建的对象；通过端口读取关系、执行继承规则、发起保存。不以单例共享可变图 |
| InheritanceStore | 窄持久化端口：锁定约定、读取角色/关系、保存边；直接边从关系快照判断。小样提供内存实现 |
| GrantPolicy | 提供本次操作者/组织/新增授权影响的校验边界；不将 Spring Security 或 HTTP 身份解析搬入领域对象 |
| 内存演示入口 | 构造可信输入和测试夹具、调用领域对象、显示结果；仅为直接运行，不新增 Web API |

小样顺序：外层建立用例边界 → FullRoleHierarchy.addInheritance → Store 锁定及装载 → Policy 检查管理范围／归属 → 自继承及幂等判断 → 对象自身查环 → Policy 校验新增授权影响 → Store 保存 → 成功后更新本次对象的内存状态 → 外层完成。

内存端口不等于真实 MySQL 事务或悲观锁。小样只能证明选定规则、职责协作和失败不保存，不能据此宣称已经通过集群并发、数据库约束、组织重授或 HTTP 授权的完整验收。真实两版的这些证据仍引用 `测试/` 报告。若以后需要满血真实数据库实现，应另行确认范围及测试，不在本轮顺便增加。

## 5. 比较方式和测试方案

比较表逐项回答：谁拥有关系数据、谁判断环路、谁校验用例边界、谁发起存储、谁负责事务、如何测试，以及一次业务规则变更会影响哪些类。

共同的手工夹具至少包括：

| 场景 | 共同规则预期 | 证明范围 |
| --- | --- | --- |
| 首次合法新增 | 恰增加一条直接边 | 三种规则/小样可对照 |
| 重复新增 | 关系不重复 | 三种规则/小样可对照 |
| 自继承 | 拒绝且关系不变 | 三种规则/小样可对照 |
| 反向边或闭合长链 | 拒绝且原关系不变 | 三种规则/小样可对照 |
| 同向传递路径上增加直达边 | 允许，权限展开去重 | 三种规则/小样可对照 |
| 菱形图及孤立分支 | 可达集合去重，不含孤立分支 | 三种规则/小样可对照 |
| 逆向影响 | 覆盖全部上游且含自身 | 三种规则/小样可对照 |
| 跨归属、越权、停用及重授 | 保持当前契约与实际持久化结果 | 正式两版真实回归；小样只展示明确实现的策略夹具 |
| 并发成环、原会话撤权 | 图无环、下一请求按新关系授权 | 正式两版 MySQL/Redis/HTTP 证据，小样不替代 |

小样使用独立手写期望值和可观察关系结果，不靠“某接口被调用几次”判断设计正确。新增行为按 TDD；对已实现规则的对照测试如直接通过，记录为既有行为验证，不制造假 RED。

现有正式回归入口及结果见 [测试说明](../测试/README.md)、[执行报告](../测试/执行报告.md)。小样测试仍集中在 `测试/`，报告单独标注，不能混入正式 func/oo 的 48/52 项数字。小样使用 Java 21 和 JUnit；不引入 Spring Boot、MySQL、Redis 或新的通用框架。

## 7. 实施顺序与完成条件

先确认术语和小样范围 → 整理真实两版比较说明 → 明确小样夹具和可观察预期 → 测试先行实现小样 → 从验证后的代码出图 → 核对图、代码、测试索引 → 补结论及答辩可复用内容。

完成条件：能用同一新增继承场景解释三种职责组织；图中每个类/方法均有代码依据；小样测试实际执行且报告明确局限；正式后端、API、Flyway 和安全语义不受影响；方案及索引同步更新。GRASP 原则可建立关联，但第 4 项现已另行形成 [系统讲解](../grasp与项目.md)，独立核对源码、图件与测试，不凭模型比较图自动标为完成。

推荐结论是比较职责和代价，而非宣称“满血一定最好”。本项目继续保留 func/oo 两条正式开发线，为 C3 提供稳定输入。
