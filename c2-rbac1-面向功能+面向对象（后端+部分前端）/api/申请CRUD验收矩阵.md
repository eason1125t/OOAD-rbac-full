# C2 申请 CRUD 契约审阅与验收矩阵

适用于面向对象版和面向功能版的共同验收。接口、参数和响应见 [共同 OpenAPI](openapi.yaml)。业务来源与交付顺序见 [开发方案](../docs/项目总结.md)。

## 已确认的契约边界

1. 新增和修改都只提交标题。驳回记录状态和操作者。展示详情时带申请人 ID，遗留记录可为空。
2. 审批与驳回继续按对应系统动作权限校验。持有权限的申请人也可以审批或驳回本人的待审批单。演示使用两个账号分别承担申请和审批职责，并单独验收本人审核。
3. 列表与详情要求目标系统的 `request:read`，适用于全部状态和历史记录。已有申请的修改、撤回、审批、驳回及删除同时要求查看权和动作权。发起申请要求 `request:create`。`allowedActions` 只返回当前可用的写动作。

## 口径

- 样例使用甲公司、工程部和财务部三个系统。申请人能进入目标系统并拥有发起和本人管理权限，审批人拥有对应审批或驳回权限。另准备同系统其他员工、不同部门员工、不同公司员工、全局管理员以及 C1 遗留申请。操作系统有同名权限时按系统 ID 分别判定。
- 业务写入先校验Bearer JWT、Redis登录状态、系统准入及所需权限；业务写入不要求Cookie CSRF（登录/刷新/退出仍校验），操作已有申请时检查查看权。修改、撤回、删除还校验申请人。服务端从可信当前员工身份取得申请人，从申请记录取得后续操作的系统。字段校验失败返回 400，鉴权失败返回 401／403，缺失或已删除返回 404，状态不允许写入时返回 409。
- 发起、修改、撤回和驳回返回申请详情。审批保持 C1 成功响应结构，删除返回 204，正常列表与详情隐藏已逻辑删除的申请。重复删除返回 404。
- 并发审批、撤回、驳回通过事务保护，只提交一个 `PENDING` 状态转换。日志中的成功写入应对应已提交结果，带版本、目标、操作者、动作和结果，拒绝或回滚也可定位。

## 按需求编号编写测试

| 验收编号 | 场景 | 主要断言 |
| --- | --- | --- |
| C2-11 | 有权申请人在目标系统发起，再读详情和分页列表 | 创建 201，返回该登录员工的申请人身份和 `PENDING`。详情和分页可查，其他系统的数据独立 |
| C2-11 | 未登录或伪造Bearer、其他部门或公司员工查询，缺少发起权限或组织已停用时发起 | 分别验证 401、403 `SYSTEM_ACCESS_DENIED` 或 403 `PERMISSION_DENIED`。失败请求不新增申请 |
| C2-12 | 本人修改待审批单并撤回，随后刷新 | 修改返回 200 且仍待审批，更新标题可查。撤回返回 200 且状态为 `WITHDRAWN`，原单仍可查询 |
| C2-12 | 空标题、超长标题或请求体试图修改申请人／状态。他人修改或撤回。编辑已撤回单、再次撤回或审批已撤回单 | 按用例验证 400 `VALIDATION_FAILED`、403 `PERMISSION_DENIED` 或 409 `REQUEST_STATE_CONFLICT`，原记录不变 |
| C2-12 | 指定不存在的系统或申请，尝试对无申请人的遗留单使用本人操作 | 分别验证 404 `SYSTEM_NOT_FOUND`、404 `REQUEST_NOT_FOUND`、403 `PERMISSION_DENIED`。遗留单仍可按 C1 准入查询和审批 |
| C2-13 | 审批人通过、驳回。申请人仅删除本人已驳回单 | 通过及驳回分别返回 `APPROVED`、`REJECTED`。重复审批已通过单返回 409 `REQUEST_ALREADY_APPROVED`。其他状态删除返回 409，他人删除返回 403，合法删除后列表及详情不再返回原单 |
| C2-13 | 同一待审批单并发审批与撤回、驳回与审批 | 每组只提交一次状态转换，失败请求返回 409，持久化状态与成功响应一致 |
| C2-14 | 对读取、写入成功、鉴权失败和状态冲突分别检查日志 | 可按版本和申请 ID 对应请求，成功仅在提交后记录，失败无成功事件，日志不包含申请正文、密码、Cookie 或 CSRF 令牌 |

| C2-15 | 缺少查看权、同系统只读、跨系统同码、继承查看权及原会话撤权 | 无查看权时列表、详情和已有申请写入为 403；独立发起可成功。只读可查全部未删除状态但无写动作，跨系统不通用。撤权后下一次读取拒绝，页面清空旧列表和详情 |
| C2-16 | 对象版申请应用服务与领域边界 | 应用服务只依赖三个申请端口，领域状态规则独立于 JPA；共同 HTTP 状态、事务和日志规则保持一致 |

执行结果见 [双版本测试记录](../测试/README.md)，其内容为既有实现的历史回归。本机重新回归已完成，最新结果与 JaCoCo、命令和输出 TXT 见 [本次执行报告](../测试/README.md)。

两版均先用 C2-11「有权员工发起申请后可在同一系统查询」确认新增路径的预期失败，再接通申请接口并执行回归。


## 集群验收衔接

本矩阵的业务预期继续用于两版 Swarm 入口；Apifox 以同一 OpenAPI 配置 C2-Swarm-func、C2-Swarm-oo 两个环境。先登录并刷新 CSRF，再逐项操作并核对对应后端 Logback；本地报告与服务器结果分别归档，详细步骤见 [部署交接文档](../部署/README.md)。
