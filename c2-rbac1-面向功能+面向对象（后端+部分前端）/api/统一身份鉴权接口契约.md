## 3. 公共认证、输入和错误约定

### 3.1 认证与可信身份

业务路径写作 /api/...，部署时加版本前缀 /func 或 /oo。例如 /func/api/auth/me；该前缀是版本路由，不是业务 systemCode。

当前后端源码使用 Spring Security Bearer JWT + Redis独立登录状态：业务请求必须携带 Authorization: Bearer；只凭刷新Cookie或旧Session Cookie不能认证。可信身份只由验签、sid记录归属/期限和最新员工资格共同确定，不接受employeeId、username或JWT角色声明覆盖当前身份。

访问JWT最长15分钟，单次登录绝对上限8小时，刷新不续期。同一账号可独立登录多个浏览器，退出只撤销当前sid。严格刷新轮换，确认已消费凭证重用时撤销整次登录；未知secret不能凭sid撤销合法登录。不使用tokenVersion或用户版本号。

GET /api/auth/csrf仍为辅助入口，返回独立HttpOnly CSRF Cookie及JSON掩码token，不创建Session或匿名Redis登录。登录、刷新和退出携带该Cookie及X-CSRF-TOKEN；登录成功和退出后重新领取CSRF。Bearer业务写入不要求CSRF，Bearer逐请求认证也不轮换CSRF。

新增POST /api/auth/refresh为辅助入口，不增加第九项业务身份能力；只读取本版HttpOnly刷新Cookie，不从body/query接收刷新凭证。访问JWT过期不阻止刷新和退出。两版使用独立密钥、issuer/audience、Cookie及Redis命名空间。生产Cookie为Secure、HttpOnly、SameSite=Strict，公开Path分别为/func/api/auth/与/oo/api/auth/；直连测试可显式覆盖为/；本机网关保持公开Path。

身份、权限和目录结果/错误使用Cache-Control: no-store；退出成功204无响应体。可信员工仍要求启用且有明确组织归属。完整配置、错误及并发边界见[JWT迁移方案](../docs/项目总结.md)，实际结果见[第三部分验证](../测试/README.md)。未开放跨项目CORS或开展项目系统联调。

### 3.2 通用输入

| 参数 | 约定 |
| --- | --- |
| systemCode | 1..64 字符，非空白，必须是已有业务系统；不从“默认工作区”悄悄推断 |
| permissionCode、operationId | 1..128 字符，非空白，按目标系统解释 |
| employeeId、departmentId、parentId | 正整数 int64，不使用外部 sso-* 标识，不增加无依据工号字段 |
| page | 默认 1，1..21474836；与现有管理分页边界一致 |
| pageSize | 默认 20，1..100；ID 稳定升序 |
| q | 最长 128，去首尾空白，空白视为无筛选；包含匹配，% 和 _ 按普通字符处理 |

分页结构固定为 {items,page,pageSize,total}。超出末页返回空 items，但 total 为当前筛选和权限范围内的总数。非法输入为 400；不允许先分页再在 Java/前端过滤可见性。

### 3.3 错误与优先级

错误体沿用 {code,message}；客户端根据 code 判断，message 可按场景说明。员工身份检查先于业务查询；通过身份后校验参数。指定系统时先定位系统，再校验系统准入，再查其中权限/API，避免泄露不可进入系统的细节。

| 场景 | HTTP / code |
| --- | --- |
| 未登录、员工已停用或无归属 | 401 AUTHENTICATION_REQUIRED |
| 登录失败 | 401 INVALID_CREDENTIALS；未知账号、错误密码、不可登录统一响应 |
| 仅访问JWT过期 | 401 ACCESS_TOKEN_EXPIRED；无效签名/错误身份不归入此类 |
| 刷新凭证无效或确认重用 | 401 REFRESH_TOKEN_INVALID / REFRESH_TOKEN_REUSED |
| CSRF 无效 | 403 CSRF_INVALID |
| 参数缺失、空白、超长、类型或组合错误 | 400 VALIDATION_FAILED |
| 未知系统 | 404 SYSTEM_NOT_FOUND |
| 系统存在但不可进入 | 403 SYSTEM_ACCESS_DENIED |
| 已准入但权限码不存在 | 404 PERMISSION_NOT_FOUND（新增） |
| 已准入但 API 映射不存在 | 404 API_NOT_FOUND（新增） |
| 已知权限/API 无权或被组织策略拒绝 | 预查询 200 allowed=false；实际操作 403 PERMISSION_DENIED |
| 无目录查询资格或数据越界 | 403 PERMISSION_DENIED |
| 组织/员工不存在 | 404 RESOURCE_NOT_FOUND；管理详情保留先资格、再存在性/范围的旧行为 |
| Redis 认证存储故障 | 503 AUTHENTICATION_UNAVAILABLE |
| 授权数据库故障/已存在映射损坏 | 503 AUTHORIZATION_UNAVAILABLE；不当作 allowed=false 或 true |
| 登录非 JSON | 415 UNSUPPORTED_MEDIA_TYPE |

## 4. ID-01 / ID-02：登录与退出

登录输入保持现有字符串账号密码：

```json
{"username":"engineering-employee","password":"1234"}
```

登录200保留employee、workspaces、defaultWorkspaceKey，新增accessToken、tokenType=Bearer、expiresIn；不在JSON中返回刷新凭证，也不返回authorization。访问凭证仅存前端内存；刷新凭证通过本版HttpOnly Cookie交付。缺少凭据或字段非法为400，凭据无效401，认证存储故障503。账号、密码和凭证不进入生产日志。

刷新200只返回accessToken、tokenType、expiresIn，并轮换刷新Cookie。expiresIn为实际剩余有效秒数，临近8小时上限可小于900。退出保持POST和204，校验CSRF后撤销当前刷新凭证对应sid并清Cookie；无/未知刷新Cookie时幂等204，存储故障不能伪装成功，不影响其他浏览器或另一版登录。刷新和退出不依赖未过期访问JWT。

前端继续现有登录页面和顶部退出入口，实际Bearer、刷新与页面恢复接入在第4部分完成；本步没有部署尚未迁移的前后端组合。

## 5. ID-03 / ID-04：自身角色与权限

### 5.1 GET /api/auth/me

省略 systemCode：返回现有员工和工作区，authorization 字段不出现（不是 null），登录成功响应也不增加授权字段。

传 systemCode：必须可进入该系统，在原响应上增加 authorization；无有效权限时返回空集合，不因为空集合把身份查询变成 403。

```json
{
  "employee":{"id":101,"username":"engineering-employee","name":"示例员工","organizationId":2},
  "workspaces":[{"key":"business:demo-engineering-app","type":"BUSINESS","name":"示例工程申请系统","path":"/business/demo-engineering-app/"}],
  "defaultWorkspaceKey":"business:demo-engineering-app",
  "authorization":{
    "systemCode":"demo-engineering-app",
    "roles":[
      {"id":10,"name":"示例高级角色","direct":true,"inherited":false,"inheritedFromRoleIds":[],"appliesToSystem":true},
      {"id":11,"name":"示例基础角色","direct":false,"inherited":true,"inheritedFromRoleIds":[10],"appliesToSystem":true}
    ],
    "effectivePermissions":[{"id":20,"code":"request:read","name":"查看申请"}],
    "globalAdministrator":false
  }
}
```

示例 ID 仅说明关系，不固定演示库主键。角色按 ID 排序去重；permissions 同样按 ID 排序。

- direct 表示直接分配；inherited 表示能从其他直接分配根角色经至少一条边到达。两者可同时为 true。
- inheritedFromRoleIds 是上述直接根角色 ID 的有序去重集合，不列完整路径，不把角色自身作为其继承根。
- roles 包含全部直接及继承可达角色；appliesToSystem 表示该角色自身或其继承闭包涉及目标系统的配置权限，不代表策略处理后有效。不新增角色—系统表。
- effectivePermissions 才是当前系统准入、角色继承、组织策略和重授之后的最终权限；系统为空、角色无贡献或被停用时，不伪造允许。
- globalAdministrator 说明当前全局管理员资格；它不能绕过组织 DISABLED，不伪造角色来源。

自身查询不要求 management:read。管理员查他人仍使用已有员工角色/有效权限管理接口，权限和响应不改。

### 5.2 GET /api/auth/me/permission-check

必填 systemCode、permissionCode。已知权限的响应固定为：

```json
{"systemCode":"demo-engineering-app","permissionCode":"request:approve","allowed":false}
```

直接使用现有系统内 request:* 权限，不增菜单/按钮类型、别名或 AuthorityCodes 表。菜单使用 request:read，按钮使用相应写动作；平台管理菜单继续按管理员资格判断。

初次加载页面使用有效权限集合批量渲染，单项检查用于单个控件刷新或权限查看，不为每个按钮逐个请求。现有申请列表 allowedActions 字段保留并复用统一计算；状态、本人归属仍由业务接口检查。后端在实际执行时重新授权。

## 6. ID-05 / ID-07 / ID-08：组织与员工目录

### 6.1 数据可见范围

| 身份 | 树/列表范围 | 员工状态与资料 |
| --- | --- | --- |
| 普通员工 | 所属部门；若直接属于公司，只可见自身公司节点及其直接归属员工，不自动扩展其部门 | 只查启用员工；列表仅 id/username/name/organizationId |
| 部门管理员 | 所管部门 | 保留旧管理字段及可查看停用员工的行为 |
| 公司管理员 | 所管公司及直属部门 | 同上 |
| 全局管理员 | 全局 | 无部门筛选时保留未匹配组织员工核对能力 |

目录范围不等于业务系统准入，不从可进入某系统推导能查询该系统所属公司的所有员工。管理员仍按 administrator_scope 读取资格/范围，不通过业务 permission 表伪造 management:read。

### 6.2 GET /api/departments

| 参数 | 行为 |
| --- | --- |
| view | directory（默认）/tree |
| parentId | tree 中查询该正式组织的直接子节点，可指公司或部门 |
| rootsOnly | tree 中 true 只查可见范围根；有 parentId 时无论 true/false 均不得同时传入 |
| q | 名称或编码包含匹配 |
| page/pageSize | 通用分页 |

directory 保留原表公司行及演示部门的旧含义，只允许管理员；可增加 q，不接受 parentId/rootsOnly。

tree 使用正式 parentId，包括 COMPANY 分组和 DEPARTMENT 节点。无 parentId/q 且省略 rootsOnly 时默认根查询；rootsOnly=false 表示可见节点平铺；仅 q 时在全部可见节点内搜索；rootsOnly=true + q 只搜根；parentId + q 只搜直接子节点。以上组合不改变范围和计数规则。

tree 示例：

```json
{"items":[{"id":2,"code":"demo-engineering","name":"示例工程部","parentId":1,"organizationType":"DEPARTMENT","hasChildren":false}],"page":1,"pageSize":20,"total":1}
```

可见根可能是本部门，但 parentId 保留真实值；hasChildren 只统计范围内正式直接子级，不受 q 的子级名称匹配影响。不存在 parentId 为 404，存在但不可见为 403；父节点不存在/越界不返回伪空列表。

本轮支持已有公司→直属部门模型的逐层读取，不承诺任意深层组织的完整准入、策略和导入。当前没有组织整体 enabled 字段，不新增该字段。

### 6.3 GET /api/employees

可选 departmentId（必须指 DEPARTMENT）、q、page、pageSize。departmentId 默认只查询直接归属员工，不增加 includeDescendants；不传则在当前可见范围内查询。q 匹配姓名或 username，不增加工号/学号概念。

数据库条件为：可见范围 AND 部门条件 AND（姓名匹配 OR 账号匹配）；count 同条件。不存在部门为 404；类型错误为 400；存在但越界为 403。普通员工不能看到停用员工，即使 q 精确匹配也不返回。

普通员工分页示例：

```json
{"items":[{"id":101,"username":"engineering-employee","name":"示例员工","organizationId":2}],"page":1,"pageSize":20,"total":1}
```

管理员保留旧 ManagementEmployeePage 字段和遮盖电话；不得返回原始电话/账号哈希。目标 OpenAPI 以 anyOf 表达这两种投影（空页可同时符合两者，不能用 oneOf 排斥空页），调用方按身份消费，不把管理员对象作为普通员工最低权限响应。

### 6.4 GET /api/employees/{employeeId}

保留管理员资格及目标可见范围；无管理员资格直接 403，具备资格后不存在 404、越界 403。普通员工通过 ID-03 读取自己，不能利用 ID-08 扩大读取他人资料，也不在本步新增普通员工详情入口。

管理员响应仍是 id、username、name、organizationId、sourceBranchName、sourceDepartmentName、jobTitle、phone（遮盖）、enabled。电话较短整段隐藏；已遮盖电话不得回填到编辑请求。原表来源字段只是核对信息，不参与授权。

前端：旧原表目录保留；管理员工页接入树筛选、搜索、分页与资料查看；普通员工业务工作区提供本组织人员列表，不显示管理角色/权限或维护按钮。

## 7. ID-06：API 权限预查询

GET /api/auth/me/api-check，必填 systemCode、operationId：

```json
{"systemCode":"demo-engineering-app","operationId":"approveRequest","allowed":true}
```

只返回系统、操作和结论，不返回所需权限集合。API 预查询只判断系统准入及系统级权限，不读取具体申请 ID，不保证某个申请存在、属于当前用户或状态允许操作。

首批系统为 demo-company-app、demo-engineering-app、demo-finance-app、demo-company-b-app；每系统映射八个申请操作：

| operationId | 所需权限（ALL） |
| --- | --- |
| listSystemRequests | request:read |
| getRequest | request:read |
| createRequest | request:create |
| updateRequest | request:read + request:update |
| withdrawRequest | request:read + request:withdraw |
| approveRequest | request:read + request:approve |
| rejectRequest | request:read + request:reject |
| deleteRejectedRequest | request:read + request:delete |

createRequest 保留当前只需 create 的行为。登录、退出、目录和授权维护等操作不属于这批业务 API 映射；不能因它们没映射就认为其实际接口不存在。其他已知业务系统尚未注册 API 映射时，本查询返回 404 API_NOT_FOUND；不把所有系统自动纳入覆盖。

所需权限来自服务端映射，不由客户端提交。固定 ALL，不实现 ANY、嵌套表达式或映射管理页面。没有映射为 404；已有映射但权限集合为空、引用丢失、跨系统或与操作要求不一致，为 503，不能空集合放行。第5步已新增Flyway V9和幂等初始化持久化，两版定义一致。V9为已有四个演示系统补32操作/52权限要求；空库由初始化在权限准备后补齐。已有损坏映射不会被初始化静默修复。

预查询结果不进入JWT或Redis权限快照缓存，不能作为目标 API 的授权凭证。目标业务接口继续按最新权限及业务对象规则检查；新增测试覆盖“预查询通过→撤权/状态变化→实际调用被拒绝”。

## 8. 实施顺序、兼容及验收
