# C2 部署交接文档

更新日期：2026-11-22。交接对象为负责课程 Docker Swarm 的队友。本文件规定部署范围、准备事项、操作顺序和验收证据；实际地址、镜像与结果待部署后填写。C2 专用构建、生产网关、stack 与初始化/凭据/备份脚本已交付，入口见 [部署包](部署说明-整理前.md)。三个镜像、独立五容器链路和日志已本机验证，课程 Swarm 调度及 Apifox 云端环境待队友实测。

## 1. 只部署 C2，目标为一前端、两后端

源码根目录是 `c2-rbac1-面向功能+面向对象（后端+部分前端）/`，下文命令除特别标注外从此目录执行。仓库中的 C1、C3 用于历史和规划，不作为本次运行服务；满血小样、UML 工具、Apifox、Navicat和测试运行器也不作为长期运行服务。

| 建议服务键 | 部署内容 | 初始副本/隔离 |
| --- | --- | --- |
| frontend | 共用 Vue 构建产物＋Nginx 或同类生产网关 | 1；同一站点提供首页、/func/、/oo/ |
| backend-func | backend-func 的 Spring Boot 应用 | 1；连接功能版库 |
| backend-oo | backend-oo 的 Spring Boot 应用 | 1；连接对象版库 |
| mysql | MySQL，创建 ooad_rbac1_func、ooad_rbac1_oo 两个数据库 | 1 个有状态服务；两个逻辑库不等于两台数据库服务器 |
| redis | 两版共用的 Redis 登录记录服务（独立随机sid） | 1；命名空间分版 |

**以上运行服务都进入 Swarm。** 老师明确要求前端、后端和数据库服务器在集群里，不能仅在集群放前端、继续连接本机 Docker Desktop 的数据库。初始单副本便于验收，不表示已具备数据库高可用。

访问流程：浏览器/Apifox → 集群入口 → frontend 网关 → 对应后端 → 集群 MySQL/Redis。日志从对应后端 Swarm 服务查看。

## 5. 路由、会话与数据库配置

### 5.1 生产网关必须实现的规则

| 外部请求 | 处理方式 |
| --- | --- |
| `/` | 展示版本选择首页 |
| `/func/`、`/oo/` 及页面深链 | 使用同一前端构建，允许刷新后回退到 index.html |
| `/func/api/...` | 代理到 backend-func 的 `/api/...`，仅去掉 `/func` |
| `/oo/api/...` | 代理到 backend-oo 的 `/api/...`，仅去掉 `/oo` |

API 匹配优先于 SPA 回退，防止接口错误被替换成 HTML。保留 Cookie、CSRF 请求头及 Set-Cookie 响应，不把两个版本 Cookie Path 都改成相同前缀。当前 Vite 的 server/preview proxy 只服务本地开发，dist 中没有能替代生产网关的代理服务。

### 5.2 后端参数

| 参数 | func | oo |
| --- | --- | --- |
| SERVER_PORT | 建议容器内 8080 | 建议容器内 8080；不同容器可用相同内部端口 |
| RBAC_DB_URL | jdbc:mysql://mysql:3306/ooad_rbac1_func | jdbc:mysql://mysql:3306/ooad_rbac1_oo |
| RBAC_DB_USER / RBAC_DB_PASSWORD | 对应应用用户/凭据 | 对应应用用户/凭据 |
| RBAC_REDIS_HOST / RBAC_REDIS_PORT | redis / 6379 | redis / 6379 |
| RBAC_REDIS_PASSWORD | 实际 Redis 配置需要时设置 | 同一实例对应凭据 |
| RBAC_JWT_ISSUER / RBAC_JWT_AUDIENCE | urn:ooad-rbac:c2:func / rbac1-func | urn:ooad-rbac:c2:oo / rbac1-oo |
| RBAC_JWT_PRIVATE_KEY_LOCATION / RBAC_JWT_PUBLIC_KEY_LOCATION | file:/run/secrets/jwt_private / jwt_public | 同名容器目标，挂载本版独立密钥 |
| RBAC_REFRESH_COOKIE_NAME | RBAC1_FUNC_REFRESH | RBAC1_OO_REFRESH |
| RBAC_CSRF_COOKIE_NAME | RBAC1_FUNC_CSRF | RBAC1_OO_CSRF |
| RBAC_AUTH_COOKIE_PATH | /func/api/auth/ | /oo/api/auth/ |
| RBAC_AUTH_NAMESPACE | rbac1:func:auth | rbac1:oo:auth |
| RBAC_AUTH_COOKIE_SECURE | HTTPS必须true；HTTP本机false | 同左 |
| RBAC_JWT_ACCESS_TTL / RBAC_LOGIN_TTL | 15m / 8h | 同左；刷新不延长绝对期限 |
| RBAC_DEMO_ACCOUNTS_ENABLED | 创建演示登录账号的初始化任务需 true | 同左 |

表中的 mysql、redis 是约定服务名示例，须与实际网络 DNS 一致。容器内不使用本机的 localhost、33327、36390，也不把后端内部端口误当作浏览器入口。JWT取消旧30分钟闲置超时，访问JWT最长15分钟、单次登录绝对8小时；不沿用任何RBAC_SESSION_*参数。已有.env中的RBAC_SESSION_COOKIE_SECURE必须显式改名为RBAC_AUTH_COOKIE_SECURE。

后端 Java 配置继续读取 `RBAC_DB_PASSWORD` 等参数；部署包的 [入口脚本](../backend-entrypoint.sh) 已实现 `RBAC_DB_PASSWORD_FILE` 与 `RBAC_REDIS_PASSWORD_FILE`，从挂载 secret 文件读取后交给应用。stack 已设置对应路径，不需把明文凭据写入配置。脱离该入口直接启动 JAR 时，不能假定 Java 应用本身自动支持 `_FILE`。secret 机制见 [Docker 官方说明](https://docs.docker.com/engine/swarm/secrets/)。

### 5.3 有状态服务和初始化

- MySQL/Redis 使用持久化卷；节点本地卷需要对应的调度约束和节点故障恢复办法，卷名相同不代表跨节点共享数据。
- 两个数据库分别迁移，应用启动执行 Flyway，Hibernate 只 validate。不得绕过迁移随意手改表结构或修改已执行脚本。
- 建议空库迁移后使用一次性任务分别执行演示初始化和 Excel 导入；禁止把两个选项放在同一次命令里。输入目录以只读挂载提供，任务调度到实际能读取输入的节点；初始化任务应单独配置为不自动重复重启，等待退出码 0 后再启动演示。不要把初始化选项留在常驻后端的启动命令中。
- `--init-demo` 配合演示账号开关生成合成账号。默认演示密码为 1234；账号清单见 [前端说明](../../docs/归档/前端说明-整理前.md)，课程访问范围与凭据由队友确认。
- 初始化不是恢复所有手工修改的重置按钮。若要保留当前角色、策略或申请，使用两库一致性备份恢复，并保留迁移历史，避免备份与初始化脚本互相覆盖。
- 主测试库与演示库分开，不把集成测试指向这两个演示库。

1. 填第 2 节参数，取得最终代码提交、课程 Excel 与必要凭据；确认这次只部署 C2。

4. 在 manager 上验证 stack 配置，先确认 MySQL/Redis 就绪及两库存在，执行迁移、一次性演示初始化和原表导入。配置校验不能代替运行验证。
5. 部署三个应用服务，检查任务与日志；数据库延迟启动时靠健康、重启或显式就绪检查处理，不只依赖 depends_on。
6. 通过集群公开入口访问首页和两版页面，核对深链、登录、CSRF、隔离和数据。

8. 执行第 8、9 节集群验收和日志留证，归档第 10 节结果；更新前备份，准备回退版本。

以下在 manager 的 C2 源码目录执行；首次生成凭据并创建 Swarm secret，按本机路径重新渲染配置。详细初始化、更新和本机验证见部署包说明：

## 7. Apifox 项目、环境和会话

### 7.1 同步正确的 C2 契约

1. 队友加入约定的 C2 项目或 C2 模块，记录项目/模块及 ID；如与 C1 共用项目，先限定导入范围。
2. 导入 [api/openapi.yaml](../../api/openapi.yaml)，当前版本2.5.0、49个操作/44个模型。核对两版共用接口，尤其新增继承、有效权限、申请 CRUD 与 request:read。
3. 更新已有接口时检查覆盖预览，不启用不明范围的“删除未匹配资源”，防止清掉 C1 或队友的测试与环境。
4. 接口路径继续是 `/api/...`，以环境前置 URL 选择 func/oo，无需复制两套接口。导入可能依据 servers 创建服务/环境，导入后核对真正生效的前置 URL。

官方参考：[OpenAPI 导入](https://docs.apifox.com/import-openapi-swagger)、[环境与前置 URL](https://docs.apifox.com/environments-and-services)。

### 7.2 新增或修改环境

| 环境名 | 前置 URL 示例 | 用途 |
| --- | --- | --- |
| C2-本地-func | http://127.0.0.1:5173/func | 本地 Vite 网关运行时调试 |
| C2-本地-oo | http://127.0.0.1:5173/oo | 同上，对象版 |
| C2-Swarm-func | https://课程入口/func | 部署后功能版验收，协议/端口用实际值 |
| C2-Swarm-oo | https://课程入口/oo | 部署后对象版验收 |

例如，选择 C2-Swarm-func 调用 `/api/auth/csrf`，最终 URL 应恰好是 `https://课程入口/func/api/auth/csrf`。避免变成 `/func/func/api/...` 或漏掉版本前缀；以发送时的实际 URL 为准。不要在共享接口路径中写死本机 IP 或某个集群域名。

环境中的用户名、密码、csrfToken、accessToken放个人本地值；共享配置只保留名称和空值/示例。环境配置与 OpenAPI 是两项交接，导入契约不能保证同步个人变量和完整测试套件。

### 7.3 JWT调试：Cookie认证入口与Bearer业务分开

1. GET `/api/auth/csrf`，保存本版Cookie，将JSON的掩码token记入个人本地csrfToken。
2. POST `/api/auth/login`，账号密码JSON及`X-CSRF-TOKEN`，自动携带Cookie；不发送Bearer。成功后把accessToken记入个人本地临时变量，刷新凭证只在HttpOnly Cookie，不从响应体取refreshToken。
3. GET `/api/auth/me`及业务请求统一用`Authorization: Bearer {{accessToken}}`。业务写入不需要CSRF，仍由服务端执行实时角色、组织及数据范围授权。
4. 登录成功会清旧CSRF；需要刷新或退出时重新GET csrf。POST `/api/auth/refresh`只带Cookie/CSRF，不带Bearer；成功后替换accessToken，Cookie自动轮换。确认旧刷新凭证重用将撤销整次sid，不能并行刷新或在结果未知时盲目重试。
5. POST `/api/auth/logout`只带Cookie/CSRF，成功204后清本地accessToken；503表示撤销未确认，不能当作已退出。访问JWT已过期仍能刷新或退出。
6. 只有明确401 ACCESS_TOKEN_EXPIRED允许协调刷新一次后重试；403、503、未知写入结果和无效签名均不能透明重放。同版切换账号后不能重发旧账号的在途写入。

func/oo分别使用RBAC1_FUNC_REFRESH、RBAC1_OO_REFRESH，公开Path为/func/api/auth/与/oo/api/auth/。HTTPS须Secure=true；直连后端调试若改Cookie Path必须使用隔离配置，正式验收优先走网关。两版独立密钥、issuer/audience与sid命名空间；不使用tokenVersion。Spring Security和Redis保留，Spring Session Redis已退出。

导入主OpenAPI时，如需保留项目根鉴权，可使用有效security逐接口展开的等价导入副本。应选择原C2模块、Method+Path覆盖、已有目录保留、不删除未匹配资源、不生成调试用例、不导入Servers/Info、不设置根鉴权，逐接口选择对应鉴权组件；无security入口选无需鉴权。契约同步和环境/调试用例适配分别验收，不把导入成功当作真实HTTP已调用。

**Apifox留证：**记录C2项目/模块、接口数、Bearer及刷新Cookie边界的回读；截图隐去真实密码、Cookie和令牌。实际课程入口、两个Swarm环境和远程请求仍待队友部署后回填。本机旧服务未换包，不能用旧Session后端验证新JWT契约。

## 8. 前端操作对应 Logback 日志

后端使用 Spring Boot/Logback 标准输出，Swarm 日志应能收集。申请审计 logger 为 `rbac1.func.request` / `rbac1.oo.request`；通用方法日志仍沿用 `rbac0.api`、`rbac0.service`、`rbac0.infrastructure` 分类名，与版本字段和服务名结合判断。

在 manager 打开两个终端，服务名按实际 stack 调整：

```bash
docker service logs --follow --timestamps c2_backend-func
docker service logs --follow --timestamps c2_backend-oo
```

再分别访问集群 `/func/`、`/oo/`：

| 前端动作 | 需要核对的日志/结果 |
| --- | --- |
| 发起或修改一条申请 | 对应后端出现 CREATE/UPDATE，操作者、系统、申请 ID 与页面一致；写入成功为 COMMITTED |
| 查看列表或详情 | LIST/DETAIL 的 SUCCEEDED，与写入提交语义区分 |
| 审批或驳回独立待审批单 | APPROVE/REJECT 及实际提交；另一版本的数据不应随之变化 |
| 触发越权或状态冲突 | 到达申请用例后记录 REJECTED 与业务码；失败状态未写入 |
| 数据库事务回滚 | 不产生该次写入的 COMMITTED，失败信息与实际事务结果一致 |

认证/CSRF 过滤器提前拒绝的请求可能没有进入申请审计，不要求它伪造业务动作日志。先保证登录与令牌正确，再演示业务拒绝。截图标明服务名、时间、版本、action、actorId、systemId、requestId、outcome/code，不包含标题正文或会话凭据。

`docker service logs` 适用于 json-file/journald 日志驱动；如课程指定集中日志平台，改用平台按服务、时间和申请 ID 定位同一记录。参见 [Docker 服务日志](https://docs.docker.com/reference/cli/docker/service/logs/)。不能用本地 IDE 日志证明集群操作。

## 9. 测试代码是否一起部署

**随仓库交付源码和报告；生产镜像只交付运行应用，测试无需成为常驻服务。** C2 教师细则要求对照需求与测试代码、运行前端并查看服务器日志，没有要求长期运行一个“测试服务”。

| 验证内容 | 推荐执行地点 | 数据/证明范围 |
| --- | --- | --- |
| 图规则、申请状态、架构等单元测试 | 开发电脑、CI 或临时构建任务 | 可现场复跑，验证对应代码规则 |
| Maven HTTP/MySQL/Redis 集成与 JaCoCo | 本地/CI 的真实依赖环境，或集群临时隔离测试环境 | 必须独立 `_test` 数据库；不触碰演示库 |
| 现有 Playwright 完整回归 | 本地独立 review 环境 | 当前配置启动本地 Vite，不直接代表远程 Swarm 已验收 |
| 部署后验收 | 本地浏览器或 Apifox 访问集群真实入口 | 证明生产网关、两版服务、数据库、JWT登录及服务器日志协作 |

现有 Maven 公共 HTTP 测试启动本地应用并严格检查测试库；运行器还依赖本机 Docker 容器，不能原样当作部署服务器测试入口。不要把它们指向演示数据库。现已提供 [外部 HTTP 冒烟](../../测试/部署/smoke.py) 和 [外部 Playwright 配置](../../测试/前端/playwright.remote.config.ts)，后者通过 RBAC_DEPLOY_BASE_URL 复用 3 项入口/双标签页测试，不启动 Vite。原有完整 23 项配置仍是本地模式，不能把该子集当成全量远程验收。

因此“本地测试通过”与“集群演示通过”都要保留。已有本地 func 48、oo 52、浏览器 23 和小样 10 项不改名为集群结果。集群至少人工执行：双入口登录/退出隔离、继承与环路拒绝、多路径与唯一来源撤权、组织停用/重授、申请生命周期、原表分页，以及对应双版 Logback。逐项关联 C2-01—C2-16，未执行项写明原因。
