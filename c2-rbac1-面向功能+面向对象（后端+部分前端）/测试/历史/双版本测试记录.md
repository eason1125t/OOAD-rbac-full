## 1. 环境和测试账号

共享前端通过同源代理将 `/func/api/` 转给面向功能版，将 `/oo/api/` 转给面向对象版。构建用 Java 21、Maven 和 Vue，浏览器使用 Edge。后端测试使用独立 MySQL 8.4 测试库 `ooad_rbac1_func_test`、`ooad_rbac1_oo_test` 和本机 Redis。浏览器测试使用两个独立的演示库，两库分别导入相同的三份课程原表。两版共用 Redis 实例，各自有会话命名空间和 Cookie。

显式启用演示初始化，各版共有八个账号，统一使用 `1234`。[全部账号和启动步骤](../../frontend/README.md)。

| 本轮新增账号 | 默认工作区 | 可用于复现 |
| --- | --- | --- |
| `engineering-requester` | 工程申请系统 | 直接获得发起、修改、撤回和删除权限。修改、撤回限本人待审批单，删除限本人已驳回单 |
| `engineering-inherited-approver` | 工程申请系统 | 分配「示例继承审批主管」和独立的申请查看角色。经由继承边到「示例继承审批来源」，获得 `request:approve` |
| `company-b-employee` | 乙公司申请系统 | 可浏览乙公司申请列表，无写入动作。访问甲公司工程系统返回 403 |

本机两库原有的工程审批策略处于重新开放状态。执行新版初始化后，用全局管理员对新增的「示例继承审批来源」重授工程审批，再运行浏览器测试。测试结束后该演示角色仍可用于审批。重复运行初始化保留现有的继承边改动与组织策略。

## 2. 两版设计差异及验收预期

两版共用 OpenAPI。同样的组织关系、授权配置、会话身份和请求状态应得到相同的 HTTP 状态、业务错误码、权限列表及持久化结果。每个库自己的 ID、时间戳、会话凭证和流水号由运行环境生成，日志的版本字段按实际服务标识。比较权限时使用本库的权限 ID，并按系统和权限码对应同一业务含义。[共同 OpenAPI](../../api/openapi.yaml)。

| 操作 | func 的实现 | oo 的实现 | 共同的验收断言 |
| --- | --- | --- | --- |
| 新增、移除直接继承 | `RoleInheritanceService.change` 编排范围、加锁、校验及写入。`RoleInheritanceRules` 接收显式关系表计算环路 | 事务由同名 Service 编排。通过 `RoleInheritanceStore` 端口读取不可变 `RoleHierarchy`，由该领域对象判断能否形成环路，JPA 适配器存储继承边 | 正常写入 204，自继承或成环 409，幂等请求保持同一关系，并发环路至多一条成功 |
| 查询直接继承、员工有效权限 | 直接边由管理查询读取。实时授权拿到关系快照后通过规则函数展开角色并计算来源 | 直接边同样由管理查询读取。实时授权调用 `RoleHierarchy.inheritedRoles`，领域对象依据自己持有的层级计算来源 | 直接边只列一跳。有效权限包含传递来源并按权限 ID 去重，按目标系统隔离 |
| 组织停用、重授和低级角色新增权限 | 分配 Service 调用显式图上的正向和反向规则，找到受影响角色，再校验范围和策略 | 分配 Service 从 `RoleHierarchy` 获取可继承角色和依赖方，事务内复用相同策略规则 | 适用的停用优先。同一个来源必须覆盖所有须重授的范围，不能将多个来源的重授拼接 |
| 发起、审批、撤回、驳回及删除 | `BusinessRequestService.applyChange` 按动作校验归属和状态，再更新实体字段 | Service 通过端口锁定、实时授权和事务，`BusinessRequest` 执行 `rename`、`withdraw`、`approve`、`reject`、`delete` 并维护自身状态 | 在相同权限、所有者和初始状态下，业务响应、并发结果、日志与最终状态一致 |
| 登录、工作区、版本切换 | `/func/` 使用 `RBAC1_FUNC_SESSION`，写入功能版 MySQL | `/oo/` 使用 `RBAC1_OO_SESSION`，写入对象版 MySQL | 两个标签页的身份、CSRF、审批数据和退出相互独立 |

核心代码可从 [功能版规则函数](../../backend-func/src/main/java/rolepermission/RoleInheritanceRules.java)、[对象版角色层级](../../backend-oo/src/main/java/rolepermission/domain/RoleHierarchy.java)、[功能版申请 Service](../../backend-func/src/main/java/simulation/BusinessRequestService.java) 和 [对象版申请实体](../../backend-oo/src/main/java/simulation/domain/BusinessRequest.java) 复核。组织策略和实时授权在两版中仍由相应 Service 负责。

## 4. 复现步骤和执行结果

1. 按 [后端运行说明](../../README.md#本机测试与启动) 准备两个测试库和 Redis，分别设置 `RBAC_DB_URL` 后执行 `mvn -f backend-oo/pom.xml verify`、`mvn -f backend-func/pom.xml verify`。测试库和演示库分开使用。
2. 在两个演示库执行显式初始化，并分别导入原表。启动功能版 18181、对象版 18182。使用全局管理员检查工程审批策略。若已重新开放，重授「示例继承审批来源」。
3. 在 `frontend/` 执行 `npm ci`、`npm run build`。设置 `RBAC_BROWSER_PREVIEW=true`、`RBAC_BROWSER_CHANNEL=msedge` 和 `RBAC_EXCEL_REVIEW_DIR`，再执行 `npm run test:e2e -- --timeout=90000`。只复验对象版可追加 `--project=oo`。
4. 手工复验实时撤权时，用两个浏览器上下文分别登录 `super-admin` 与 `engineering-inherited-approver`。在待审批单上验证审批可用。管理员移除「示例继承审批主管 → 示例继承审批来源」，保持审批人会话，尝试审批另一张待处理单。旧页面仍显示审批按钮时，用它验证服务器的拒绝。复验后由管理员恢复继承边。

只复验角色权限页时，执行 `npm run test:e2e -- role-permissions.spec.ts --project=oo --project=func`。复用已启动的 Vite 预览时，将 `RBAC_REUSE_FRONTEND` 设为 `true`，并用 `RBAC_FRONTEND_TEST_PORT` 指定实际端口。展示用例读取预置的「测试工程主管」，两个写入用例使用独立的临时角色，结束时清理其继承边、直接授权和角色。专项不需要导入 Excel。

| 执行项 | 结果 |
| --- | --- |
| func `mvn test` | 46 项通过，零失败、零错误、零跳过 |
| oo `mvn test` | 50 项通过，零失败、零错误、零跳过；含 3 项申请领域测试和 1 项架构依赖检查 |
| Vue 类型检查和生产构建 | 角色权限页实现完成时已通过 |
| Edge 角色权限专项 | 6 项通过，oo、func 各 3 项 |
| Edge 全量回归 | 23 项通过。oo、func 各 11 项，另有双标签页 1 项。含两版 Excel 全量核对 |

2026-11-19 的查看权修复先在功能版观察到列表应为 403、实际为 200 的失败。前端修复也先观察到刷新已返回 403，但旧表格仍有 8 行的失败。补齐清空行为后，查看权场景在两版浏览器通过。对象版新增架构测试先因应用服务仍依赖 JPA 仓储而失败，迁到端口后通过。CloneFactory 映射已全量重新编译，并核对生成代码包含 ID、标题、状态和可空申请人的赋值。

两版演示库均从 V7 升至 V8，数据库记录 `success=1`，各有四个演示系统的 `request:read` 定义。升级保留历史申请。合成账号通过独立的查看角色授权，普通既有角色的动作权限仍需管理员补查看权。

演示账号初始化采用测试先行。改动前两版都因仅有五个演示员工而失败。改动后，新增账号的权限断言与重跑保留撤权的断言一并通过。首次完整浏览器运行时，功能版两项用例在退出请求完成前触发跨页面导航，等待下一账号的登录表单时超时。脚本现等待退出后的登录页，再发起下一次登录。

本机后端复验日志保存在两版各自的 `target/c2-read-ports-verify.log`，全量浏览器输出保存在 `backend-oo/target/c2-read-ports-e2e.log`。测试结果可用 [共同测试](../前端/tests) 重新生成。
