# 第六步：统一身份功能的前端接入

日期：2026-11-21（Asia/Shanghai）。本步接入第五步已验证的后端，不修改Java授权规则或数据库迁移。保留现有Vue页面、两版入口与Session Cookie流程。

## 已完成与使用方式

| 位置 | 使用方式及接口 |
| --- | --- |
| 登录、顶部身份和退出 | 沿用现有App会话外壳、CSRF轮换和工作区导航 |
| 业务申请页“我的角色与权限” | 展开查看当前系统、直接/继承角色及来源、系统相关性和有效权限；调用带systemCode的/api/auth/me |
| 面板内“检查前端权限” | 输入已有权限码，调用/api/auth/me/permission-check；区分允许、不允许与未知权限错误 |
| 面板内“检查 API 权限” | 选择八种现有申请操作，调用/api/auth/me/api-check；错误不显示为无权限，旧结论不会沿用 |
| 申请列表及动作按钮 | 共用当前系统有效权限快照；列表受request:read控制，发起只需request:create，其余动作仍结合当前申请状态和本人归属 |
| 顶部“部门与员工” | 两版及管理/业务工作区共用入口，按需加载根部门或直接子部门；公司用于逐层展开，部门用于筛选员工 |
| 部门与员工弹窗 | 支持部门名称/编码搜索、员工姓名/账号搜索、部门分页和员工分页；筛选改变回到第1页 |
| 管理员“查看资料” | 在相同弹窗中调用/api/employees/{employeeId}；普通员工不提供此入口，后端仍独立拒绝越权查询 |

无查看权时清空旧列表和详情，显示明确说明；如仍有发起权，保留发起按钮并可实际提交。不会因为列表无法读取而取消独立发起权。没有当前权限快照或请求失败时，不沿用旧角色、列表、详情和按钮授权。

部门与员工列表范围由后端执行。普通员工只接收最小身份字段，管理员资料沿用已遮盖电话；前端不下载完整目录后自行过滤，也不向普通员工请求管理员目录或资料。部门搜索使用view=tree，原管理员“部门目录”及其原表字段继续保留。

## 文件与协作

| 文件 | 职责 |
| --- | --- |
| frontend/src/api.ts | 补充自身授权/两类检查、树节点、最小员工及管理员资料类型；沿用同源请求和统一错误 |
| frontend/src/BusinessPage.vue | 读取指定系统授权并控制列表/按钮，复用原实际申请操作和结果反馈 |
| frontend/src/CurrentAccess.vue | 展示父页面传入的授权快照，调用两类自身检查，不使用管理员查人接口 |
| frontend/src/DepartmentEmployees.vue | 共用逐层目录、搜索分页及受保护资料查询；独立维护请求状态 |
| frontend/src/App.vue、style.css | 共用入口、弹窗及响应式布局，保留原页面风格 |
| 测试/前端/tests/identity.spec.ts | 两版新增界面、边界和故障展示验收 |
| 测试/脚本/run_frontend_identity.py | 构建、初始化独立UI测试库、启动临时后端、执行浏览器、归档并停止自己启动的进程 |

异步目录/资料请求使用递增序号，旧响应不得覆盖新筛选；检查输入或授权快照变化即清空旧结论。错误、空结果、加载与允许/拒绝分别展示。小屏布局限制弹窗内部宽度，表格在自身容器滚动，长目录在弹窗内垂直滚动。

不增加JWT、跨项目CORS、第三套后端、课程教师学生业务、新映射管理页或测试依赖到frontend。正式接口全集仍为OpenAPI2.4.0，无新增契约变更。
