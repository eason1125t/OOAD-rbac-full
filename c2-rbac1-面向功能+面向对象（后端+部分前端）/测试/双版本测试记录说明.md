## 2. run_backend.py 到底运行什么

运行一次脚本，只选择一个后端版本：

```powershell
# 在 C2 目录执行
python ./测试/脚本/run_backend.py func
python ./测试/脚本/run_backend.py oo
```

两行依次执行时，先完成 func，再执行 oo。脚本不是把 Java 文件逐个当作程序启动，而是准备依赖环境后调用该版 `mvn -f backend-<版本>/pom.xml verify`。

实际流程为：

1. 检查命令参数，只接受 func 或 oo；读取本机已有 C2 MySQL 容器配置，凭据只进入子进程环境，不写入命令 TXT。
2. 为所选版设置专用测试库、Redis 地址；Maven 同时注入 `rbac.test.edition`。公共契约还在 Spring 启动前校验版本与测试库是否匹配。
3. Maven 编译生产和测试源码。该版的测试源码来自 `后端/func/java` 或 `后端/oo/java`，公共测试来自 `后端/common/java`。
4. Surefire/JUnit 发现测试类中的测试方法并执行。辅助类、普通方法、没有测试标记的代码不会因为文件位于目录中就单独算一次测试；参数化方法可产生多次执行。
5. 当前没有配置整套 Java 测试类并行执行，具体先后由 Surefire/JUnit 调度，不承诺固定的测试类顺序。测试中的并发场景会自行启动竞争请求，这是单个用例的内容，不代表所有测试类同时并发。
6. `verify` 继续生成 JaCoCo 报告并完成 Maven 后续验证；脚本汇总 Surefire XML，复制 JaCoCo HTML/XML，保存命令、完整输出、时间、退出码、代码摘要及统计。
7. Maven 失败或出现失败、错误、跳过时，脚本返回非零退出码，不能作为完整通过。脚本不会启动浏览器、运行 Playwright 或生成 JaCoCo 截图。

脚本把 Maven 完整输出重定向到 `结果/<版本>/命令行输出.txt`，终端通常在结束时才显示 JSON 汇总；暂时没有终端输出不等于卡住。Docker 和数据库必须已经可用，脚本不负责自动启动容器。

## 4. 两版设计差异与共同结果

| 操作 | func 的实现 | oo 的实现 | 必须保持的外部结果 |
| --- | --- | --- | --- |
| 继承图计算 | RoleInheritanceGraph 保存关系，静态 RoleInheritanceRules 计算可达性与反向关系 | RoleHierarchy 持有不可变快照并执行领域图规则 | 相同根和边得到相同闭包，拒绝自继承及环路 |
| 继承写入 | 具体继承存储配合 Service、AssignmentService 校验 | 继承仓储端口及 JPA 适配器，领域对象承担图规则 | 正常及幂等写入204；成环或不同归属409；越权403 |
| 实时授权 | Service 组合直接角色、图闭包和组织策略 | 相同组织策略 Service，闭包来自 RoleHierarchy | 停用优先；同一直接权限来源满足全部适用重授；原会话撤权生效 |
| 申请状态 | Service 的静态 applyChange 校验并修改 JPA 托管字段，事务脏检查保存 | 应用服务依赖三个端口，BusinessRequest 校验状态，适配器显式保存 | 查看权、动作权、本人边界、状态码和最终状态一致 |
| 对象映射 | 从持久化申请映射服务结果，再映射公开 VO | 从领域申请映射服务结果，再映射公开 VO | 均使用现有 CloneFactory，公开字段和历史空申请人兼容 |
| 会话和日志 | FUNC Cookie、func 测试库、rbac1.func.request | OO Cookie、oo 测试库、rbac1.oo.request | 身份、CSRF和写入隔离；日志版本标识分别正确 |

ID、时间戳、会话凭证不要求两版数值相同。比较的是同一业务规则的 HTTP 状态、错误码、权限含义、数据状态和拒绝后的不变性；本轮没有做全库逐行二进制相等比较。

### 5.1 本轮补充的图规则操作

两版都手写同一个菱形图：`1→2、1→3、2→4、3→4`，另有不相关分支 `9→10`。

| 测试方法 | 操作 | 独立给定的预期 | 两版结果 |
| --- | --- | --- | --- |
| expandsDiamondWithoutDuplicates | 从1展开所有来源 | 集合恰为{1,2,3,4}，4只计一次，9/10不进入结果 | 均通过 |
| findsAllDependingRoles | 从4沿反向关系查受影响角色 | 集合恰为{1,2,3,4}，包含自身及全部上游 | 均通过 |

#### C. 查看直接继承边

SELECT senior.name AS senior_role, junior.name AS junior_role

SHOW CREATE TABLE role_inheritance;
SELECT id FROM role_hierarchy_lock;

**预期检查点**：继承组合主键防重复，两个角色外键保护引用，CHECK拒绝自继承，锁表预置id=1。更长环路和同归属规则仍由后端业务入口校验，不能以这些DDL约束代替业务验证；这两条补充命令未在本次记录编写时执行。

#### D. 展开直接与传递来源，查询候选权限

```sql
WITH RECURSIVE role_sources(role_id) AS (
    SELECT er.role_id
    FROM employee_role er
    JOIN employee e ON e.id = er.employee_id
    WHERE e.username = 'engineering-inherited-approver'

    UNION DISTINCT

    SELECT ri.junior_role_id
    FROM role_sources rs
    JOIN role_inheritance ri
      ON ri.senior_role_id = rs.role_id
)
SELECT DISTINCT p.id, p.code, p.name, bs.code AS system_code
FROM role_sources rs
JOIN role_permission rp ON rp.role_id = rs.role_id
JOIN permission p ON p.id = rp.permission_id
JOIN business_system bs ON bs.id = p.system_id
WHERE bs.code = 'demo-engineering-app'
ORDER BY p.id;
```

**此前功能版只读查询结果**：返回request:approve（工程申请审批）及request:read（查看申请），目标系统为demo-engineering-app。继承闭包包含根角色，DISTINCT消除重复角色或权限路径的重复展示。

这只是“角色关系提供的候选权限”，没有完整执行员工有效性、系统准入、组织停用和同源重授规则。最终是否允许操作仍以统一授权Service及实际HTTP响应为准。

#### E. 查询申请状态和组织策略

在工程系统选定一张待审批申请，记下其ID。先执行以下查询记录状态；前端操作后重新执行，并在结果中定位同一ID，不凭最新一行猜测操作目标。

```sql
SELECT id, applicant_id, status, deleted_at
FROM simulated_request
WHERE system_id = (
    SELECT id FROM business_system WHERE code = 'demo-engineering-app'
)
ORDER BY id DESC
LIMIT 10;
```

组织策略和重授来源使用：

```sql
SELECT
    o.name AS organization_name,
    op.status,
    p.code AS permission_code,
    r.name AS regranted_source_role
FROM organization_permission op
JOIN organization o ON o.id = op.organization_id
JOIN permission p ON p.id = op.permission_id
JOIN business_system bs ON bs.id = p.system_id
LEFT JOIN organization_permission_regrant g
  ON g.organization_id = op.organization_id
 AND g.permission_id = op.permission_id
LEFT JOIN rbac_role r ON r.id = g.role_id
WHERE bs.code = 'demo-engineering-app'
  AND p.code = 'request:approve';
```

**判定方式**：无策略记录时按项目默认开放规则处理；DISABLED应阻止适用范围内操作。REOPENED不等于所有普通员工自动恢复，须由同一个直接权限来源角色满足全部适用重开范围。当前记录没有用户提供的这两组查询结果，不标记为本次手工验证通过。
