现存历史业务回归记录使用真实 MySQL 8.4 和共享 Redis，功能版通过 46 项、对象版通过 50 项后端测试，零失败、零跳过。对象版另有纯领域与端口依赖检查。六个申请 HTTP 集成用例覆盖申请人归属、状态迁移、本人审核、请求校验、并发和日志。两库已应用 V6、V7 和 V8。V8 补齐申请查看权限，普通业务账号需明确获得 request:read。Flyway 仍提示 MySQL 8.4 超出当前版本验证范围。

共享前端通过类型检查和 Vite 构建。Edge 共通过 23 项端到端测试，两版各跑 11 项，另用同一浏览器的两个标签页验证独立登录、写入和退出。两库分别导入课程原表并逐页对照 10,000 条员工、111 条组织目录及 359 条功能权限清单字段，同时核对 54 条未匹配标记和电话脱敏。八个演示账号密码均为 `1234`，启用方式见 [前端运行与验收](./frontend/README.md)。

本次文档同步未重跑业务测试。下列命令仍适用于现有测试位置；后续 `测试/` 目录及运行入口建成后再同步替换，并集中保存 JaCoCo 结果图、命令和命令行输出 `.txt`。

## 本机测试与启动

1. 使用 Java 21 和 Maven。若本机尚无 CloneFactory 制品，从 C2 目录运行 `mvn -f backend-func/tools/clonefactory/pom.xml install`，两版使用相同制品。
2. 启动本机 MySQL 和 Redis，为测试准备 `ooad_rbac1_func_test` 和 `ooad_rbac1_oo_test`。配置 `RBAC_DB_USER`、`RBAC_DB_PASSWORD`、`RBAC_REDIS_PORT`，按需设置 `RBAC_REDIS_HOST`。在 C2 目录先将 `RBAC_DB_URL` 指向功能测试库并运行 `mvn -f backend-func/pom.xml verify`，再指向对象测试库并运行 `mvn -f backend-oo/pom.xml verify`。未选择对应测试库或未设置 Redis 端口时，C1 继承来的真实依赖用例会跳过。
3. 单独验证继承规则可运行 `mvn -f backend-func/pom.xml -Dtest=RoleInheritanceRulesTest test` 或 `mvn -f backend-oo/pom.xml -Dtest=RoleHierarchyTest test`，无需启动数据库和 Redis。
4. 启动应用前准备对应的开发库 `ooad_rbac1_func`、`ooad_rbac1_oo`。各进程使用自己的 `RBAC_DB_URL`，运行对应的 `target/rbac1-<版本>-0.1.0-SNAPSHOT.jar`。本地直连调试可设置 `RBAC_SESSION_COOKIE_PATH=/`。同机并行运行时给两版设置不同的 `SERVER_PORT`。

## 继承表与事务

Flyway V6 新增 `role_inheritance`，由 `senior_role_id` 指向提供权限的 `junior_role_id`。使用两列组合主键防重，两列分别外键引用 `rbac_role.id`，增加逆向索引和两列不同的检查约束。新增边可从低级角色沿现有边到达高级角色时闭环，必须在事务内做应用校验。采用预置的数据库锁记录串行化依赖当前继承图的写入，通过真实 MySQL 上的并发 HTTP 测试验证，即使两条候选边端点互不重叠，也只能提交其中一条。

## 角色继承测试矩阵

两版使用同一工程部样例。主管继承班组长，班组长继承审批员。审批员直接持有工程系统审批权限，员工只获分配主管。测试独立初始化申请和角色关系。

| 验收 | 测试输入与预期 | 当前进度 |
| --- | --- | --- |
| C2-01、C2-02 | 为主管增加直达审批员的边，两个来源路径同时存在，权限列表仅返回一次审批权限 | 两版 HTTP 验收通过 |
| C2-03 | 自继承、沿已有一跳或两跳路径添加反向边，均判定成环。已有间接路径时新增同方向的直达边，仍然合法 | 两版规则单测已覆盖 |
| C2-03、C2-05 | 同时提交两条会共同闭环的边，最终只保存一条。不同归属的角色禁止连边，合法重复增删幂等 | 两版 HTTP 及 MySQL 约束验收通过 |
| C2-04 | 原会话审批成功，管理员删掉最后一条路径后，原会话审批另一条申请返回 403。数据库仍为待审批 | 两版原会话审批验收通过 |
| C2-06、C2-07 | 同一来源覆盖全部适用重授范围才获权，且停用优先。继承及分配写入须核对新增权限和涉及组织 | 两版验证停用优先、同源重授及授角和授权限检查 |

两版均在浏览器复验了环路冲突后的操作、多个路径的权限去重、共享边的维护范围和逐条撤权。移除直达边后，员工沿传递链仍可审批。移除最后一条路径后，原会话的下一次审批返回 403，申请仍待审批。参见 [双版本测试记录](./双版本测试记录.md)。

## 两版申请接口联调

使用 [共同 OpenAPI](./api/openapi.yaml) 的申请列表和写入接口。为目标系统配置并授权 `request:create`、`request:update`、`request:withdraw`、`request:approve`、`request:reject` 和 `request:delete`。列表和详情要求 request:read，处理已有申请还需查看权。修改及撤回要求本人且待审批，删除要求本人且已驳回。账号可以按自己的系统权限审批或驳回本人申请。原有 C1 申请仍可审核，申请人为空时无法进行本人专属操作。

功能版用 `rbac1.func.request`，对象版用 `rbac1.oo.request` 记录申请操作结果，包括版本、操作者、系统和申请 ID。写入在事务提交后记录成功。业务拒绝或回滚按失败结果记录。可用同一账号分别发起申请并比较响应、详情及 Logback 输出。参见 [申请 CRUD 验收矩阵](./api/申请CRUD验收矩阵.md)。
