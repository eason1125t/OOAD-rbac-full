# C2 StarUML 图件复核与补齐记录

日期：2026-11-19。范围：当前本地前后端实现、共同 OpenAPI 2.1.0、Flyway V1–V8 及现有测试源码。原有 16 张复核后保留编号，补充 26 张，共 42 张。所有模型和图片见 [逐图索引](./图件索引.md)。本轮没有修改业务实现、提交或推送 Git。

## 依据与范围

已读取老师 [UML skill](../../../项目整体方向规划和技术细节/老师提供的skill/uml-class-sequence-diagrams/uml-class-sequence-diagrams/SKILL.md) 及 [检查清单](../../../项目整体方向规划和技术细节/老师提供的skill/uml-class-sequence-diagrams/uml-class-sequence-diagrams/references/checklist.md)。类图与时序图按其中的 Service 居中、字段关联、依赖与实现箭头、MetaClass、消息、执行条、异常及控制片段要求核对；ER、组件、活动与状态图使用各自图法。课堂重点从同一请求的两版实现差异展开，不能把 OO 的包名或接口数量当作设计质量的证明。

本轮按用户确认，只画已实现内容。本记录对应原有 42 张图；后续完成的三模型比较、满血内存小样及两张新增图见 [独立比较目录](../../三模型比较/README.md)，不并入本批次统计。课程 Swarm 尚未部署，不将本地 Vite 代理画成已经落地的集群拓扑。图件是所选用例的说明，不是所有接口、异常和整个系统依赖的穷举。

## 发现与修正

| 发现 | 修正及影响 |
| --- | --- |
| 原方法签名含手工缩写，可能与实际泛型和参数名不同 | 从 Java 声明读取参数、返回类型、可见性和 static；部分长签名折叠显示名称，完整参数保存在 UML 模型 |
| 只验证类文件或字段文本出现，不足以防止伪造字段关联 | 关联要求实际字段声明；补入不存在关联字段必须失败的防错测试 |
| 自继承时实际复用 senior，原时序仍重复查 junior | junior 查询放入 `seniorId ≠ juniorId` 的 opt |
| 跨请求验收的三个顺序步骤使用 opt，容易被理解为可选 | 改用 seq，明确删边事务提交后才发起原员工会话的下一次请求 |
| func 的静态 applyChange 被画成实例自调用 | 审批及 CRUD 补图增加 `«MetaClass» : BusinessRequestService`，由其调用 JPA 实体 setter；OO 继续调用领域对象行为 |
| 事务提交后的日志原来只有注记 | 图 38 明确 record 注册同步回调、方法返回、事务提交及 afterCompletion 后记 COMMITTED；未提交和拒绝日志在注记区分 |
| 只检查消息发送时激活，不能保证同步接收者在调用者结束前完成 | 增加完整执行区间检查，修正提交与回调的执行条长度 |
| 组织策略保存写成字段参数简写 | 改成实际 `save(new OrganizationPermission(...))` / `save(new PermissionRegrant(...))`，保留权限行锁及重授先角色后权限锁次序 |
| 补图初稿使用了不存在的 ManagementWriteService 名称 | 核对源码后改为实际 ManagementMaintenanceService |
| 前端补图初稿将权限弹窗直接挂在 AdminConsole 下 | 改为实际由 AdminDirectory 承载；区分导入依赖及 HTTP 协作 |
| Excel 浏览容易被画成一次加载全体员工 | 图 37 分开目录按需翻页与表单选择项 allPages 循环，明确每页 100 条和退出条件 |
| 删除任何一条继承边都拒绝的理解不准确 | 图 42 增加仍有有效来源则允许、唯一来源失效则拒绝的分支，并保留停用与同源重授约束 |
| 陈氏 ER 角色容易被画成两个实体，主标识下划线可能被白底遮住 | 同一个角色实体连接递归继承的 senior/junior 两端；下划线置于属性椭圆上层 |

## 执行与证据

在 C2 目录执行：

```powershell
python ./docs/design/test_diagram_checks.py
./docs/design/export-staruml.ps1
python ./docs/design/build_staruml.py --check
```

| 本轮检查 | 结果 |
| --- | --- |
| 生成阶段源码、API、测试入口与输入布局校验 | 42 张全部通过 |
| 绘图工具回归 | 8 项通过；不存在字段关联用例先观察到失败，再补强校验后通过 |
| StarUML 官方 CLI 导出 | SVG、PNG 分别报告 `Total 42 diagrams were exported` |
| 图源完整性 | 2,978 个唯一图元，6,647 个引用全部解析 |
| 实际类图渲染布局 | 73 个类框无重叠，实际关系线无穿框 |
| PNG 目视 | 42 张由 PNG 总览逐张检查；关键静态调用、组织策略、提交回调及 ER 主标识另放大复核 |
| 文档与迁移对照 | 382 个本地文档链接有效；两版 V1–V8 迁移内容一致，模型与索引的 42 个图名一一对应 |
| 业务测试 | 本轮未重跑；索引引用现有测试，原业务结果仍见双版本测试记录 |

`--check` 读取已落盘模型与导出；生成阶段才执行源码和消息区间检查，故完整复验要运行导出脚本而不只是 `--check`。脚本不会更改业务库。PNG 只合成白底；本机 StarUML 试用水印保留，正式展示可由有许可的 StarUML 重新导出。自动检查主要覆盖模型引用、输入布局及实际类框，其他图的可读性仍由目视复核保障。

## 使用建议与待办

课堂主线建议选“新增继承 → 查询有效权限 → 原会话实时撤权 → 申请状态变化”，对照两版类图与时序，补充材料按追问打开，不必顺序展示 42 张。后续按 [C2 收尾清单](../../收尾清单.md) 六项顺序推进；代码整理或测试目录调整时同步图件与索引。后续模型比较和 [GRASP 专项](../../grasp与项目.md) 已另行完成；Swarm 仍由队友实际部署后补部署拓扑、服务日志与集群验收证据。本记录保留图件生成阶段的验证事实。
