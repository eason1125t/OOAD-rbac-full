# C2 数据库逻辑与图件对照

2026-11-19 核对两版现有 Flyway V1–V8。本说明解释已经实现的结构，不新增迁移。功能版使用 `ooad_rbac1_func`，对象版使用 `ooad_rbac1_oo`；两版表结构一致，后续写入各自独立。Redis 可以共用实例，但仅保存按版本隔离的登录会话，不复制两库业务数据。

## 角色继承

对应图 17 陈氏 ER、图 18 逻辑 ER，源码为两版 [V6](../../backend-oo/src/main/resources/db/migration/V6__create_role_inheritance.sql)。

| 表与列 | 类型及约束 | 含义 |
| --- | --- | --- |
| `rbac_role.id` | `BIGINT` 主键 | 继承两端都是同一角色实体 |
| `rbac_role.owner_organization_id` | 可空 `BIGINT`，FK → `organization.id` | 空表示共享角色；非空表示所属组织 |
| `role_inheritance.senior_role_id` | 非空 `BIGINT`，FK → `rbac_role.id` | 获得继承权限的高级角色 |
| `role_inheritance.junior_role_id` | 非空 `BIGINT`，FK → `rbac_role.id` | 提供权限的低级角色 |
| `role_hierarchy_lock.id` | 非空 `INT` 主键，CHECK `id=1`，预置一行 | 串行化所有依赖当前继承图校验的写操作；与角色无外键 |

继承表组合主键 `(senior_role_id,junior_role_id)` 防重复，索引 `ix_role_inheritance_junior(junior_role_id)` 供逆向查找。CHECK `senior_role_id <> junior_role_id` 只阻止直接自继承，不能阻止传递环。应用层在同一事务中先锁图，再读取当前边并检查管理范围、同归属、环路和增量授权。双方共享可连边，但只有全局管理员可维护共享图。高级角色沿 `senior → junior` 获得权限；直接边落库，可达闭包通过内存 Set 计算，多路径不重复落边或重复输出权限。

锁顺序以当前实现为准：继承、角色删除及两类分配写入首先取得图锁，再沿用相关实体锁与权限锁；继承维护采用 `READ_COMMITTED`。数据库写锁供多个应用进程共同使用，不依赖单机 Java 锁。读操作不把权限写入会话；管理员事务提交后，员工下一次请求重新查询当前数据库。

## 申请生命周期

对应图 19 逻辑 ER、图 25 状态图、图 41 并发活动图。结构由 [V4](../../backend-oo/src/main/resources/db/migration/V4__create_simulated_request.sql) 建表并由 [V7](../../backend-oo/src/main/resources/db/migration/V7__extend_simulated_request_lifecycle.sql) 扩展。

| `simulated_request` 列 | 类型及约束 | 用途 |
| --- | --- | --- |
| `id` | 自增 `BIGINT` 主键 | 申请标识 |
| `system_id` | 非空 `BIGINT`，FK → `business_system.id` | 鉴权系统来自持久化记录 |
| `title` | 非空 `VARCHAR(128)` | 唯一可修改业务字段 |
| `status` | 非空 `VARCHAR(16)`，默认 `PENDING` | CHECK 限定 `PENDING/APPROVED/WITHDRAWN/REJECTED` |
| `applicant_id` | 可空 `BIGINT`，FK → `employee.id` | 新单使用当前服务端身份；旧单保留空值 |
| `deleted_at` | 可空 `DATETIME(6)` | 非空仅允许状态为 `REJECTED` |
| `created_at/updated_at` | 非空 `DATETIME(6)` | 数据库默认时间及更新时点 |

保留索引 `ix_simulated_request_system_id(system_id,id)`，新增 `ix_simulated_request_visible(system_id,deleted_at,id)`。列表、计数、详情和加锁查询均排除逻辑删除。删除只设置 `deleted_at`，不产生 `DELETED` 状态。历史申请人为空时不能执行本人专属修改、撤回或删除，仍可按权限查看、审批与驳回。

已有申请写入先以 `PESSIMISTIC_WRITE` 锁定当前行，再检查查看权、动作权和状态。功能版在 Service 的静态 `applyChange` 中检查状态，JPA 脏检查保存；对象版由 `BusinessRequest` 执行状态转换，仓储适配器映射并保存。对同一待审批单竞争审批／撤回／驳回，仅一个状态转换提交，其余按最新状态返回冲突。允许拥有权限者自审核；撤回不能重提；仅本人可删除已驳回申请。

## 组织策略及实时授权

[V5](../../backend-oo/src/main/resources/db/migration/V5__add_scoped_permission_regrants.sql) 将直接组织策略扩展为 `OPEN/DISABLED/REOPENED`。`organization_permission_regrant` 组合主键为 `(organization_id,role_id,permission_id)`，分别以组合外键引用组织策略和角色直接权限；角色直接权限被删除时，其对应重授级联删除。

停用先锁目标权限行，保存 `DISABLED`，清理本组织及直接下属组织的旧重授。重开仅将原 `DISABLED` 改成 `REOPENED`，不会自动恢复旧重授。显式重授要求来源角色直接持有权限、目标组织已重开且适用组织链无停用。

授权先检查系统准入，任何适用 `DISABLED` 均优先拒绝，包括全局管理员。普通员工需要有效角色来源；存在多个 `REOPENED` 时，同一个直接权限来源角色必须满足全部适用重授，不能拼接不同来源。图 23、27/29、42 展示这些规则。图件只选择主题相关列，省略通用字段的地方不代表数据库没有这些字段。

| 表 | 核对内容 |

#### B. 查看员工直接分配的角色

SELECT e.username, r.id AS role_id, r.name AS role_name

#### C. 查看直接继承边

```sql
SELECT senior.name AS senior_role, junior.name AS junior_role
FROM role_inheritance ri
JOIN rbac_role senior ON senior.id = ri.senior_role_id
JOIN rbac_role junior ON junior.id = ri.junior_role_id
WHERE senior.name = '示例继承审批主管';
```

**此前功能版只读查询结果**：存在“示例继承审批主管 → 示例继承审批来源”。高级角色是接收方，低级角色是权限来源方。

如需查看数据库约束，可另执行：

```sql
SHOW CREATE TABLE role_inheritance;
SELECT id FROM role_hierarchy_lock;
```

**预期检查点**：继承组合主键防重复，两个角色外键保护引用，CHECK拒绝自继承，锁表预置id=1。更长环路和同归属规则仍由后端业务入口校验，不能以这些DDL约束代替业务验证；这两条补充命令未在本次记录编写时执行。

#### D. 展开直接与传递来源，查询候选权限

```sql
WITH RECURSIVE role_sources(role_id) AS (
    SELECT er.role_id
    FROM employee_role er
    JOIN employee e ON e.id = er.employee_id
    WHERE e.username = 'engineering-inherited-approver'

    UNION DISTINCT

    SELECT ri.junior_role_id
    FROM role_sources rs
    JOIN role_inheritance ri
      ON ri.senior_role_id = rs.role_id
)
SELECT DISTINCT p.id, p.code, p.name, bs.code AS system_code
FROM role_sources rs
JOIN role_permission rp ON rp.role_id = rs.role_id
JOIN permission p ON p.id = rp.permission_id
JOIN business_system bs ON bs.id = p.system_id
WHERE bs.code = 'demo-engineering-app'
ORDER BY p.id;
```

**此前功能版只读查询结果**：返回request:approve（工程申请审批）及request:read（查看申请），目标系统为demo-engineering-app。继承闭包包含根角色，DISTINCT消除重复角色或权限路径的重复展示。

这只是“角色关系提供的候选权限”，没有完整执行员工有效性、系统准入、组织停用和同源重授规则。最终是否允许操作仍以统一授权Service及实际HTTP响应为准。

#### E. 查询申请状态和组织策略

在工程系统选定一张待审批申请，记下其ID。先执行以下查询记录状态；前端操作后重新执行，并在结果中定位同一ID，不凭最新一行猜测操作目标。

```sql
SELECT id, applicant_id, status, deleted_at
FROM simulated_request
WHERE system_id = (
    SELECT id FROM business_system WHERE code = 'demo-engineering-app'
)
ORDER BY id DESC
LIMIT 10;
```

组织策略和重授来源使用：

```sql
SELECT
    o.name AS organization_name,
    op.status,
    p.code AS permission_code,
    r.name AS regranted_source_role
FROM organization_permission op
JOIN organization o ON o.id = op.organization_id
JOIN permission p ON p.id = op.permission_id
JOIN business_system bs ON bs.id = p.system_id
LEFT JOIN organization_permission_regrant g
  ON g.organization_id = op.organization_id
 AND g.permission_id = op.permission_id
LEFT JOIN rbac_role r ON r.id = g.role_id
WHERE bs.code = 'demo-engineering-app'
  AND p.code = 'request:approve';
```

**判定方式**：无策略记录时按项目默认开放规则处理；DISABLED应阻止适用范围内操作。REOPENED不等于所有普通员工自动恢复，须由同一个直接权限来源角色满足全部适用重开范围。当前记录没有用户提供的这两组查询结果，不标记为本次手工验证通过。
