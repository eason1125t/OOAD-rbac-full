## 4. 五项功能的接口提案

通用约定：GET + Session；敏感结果 Cache-Control: no-store；分页沿用 `{items,page,pageSize,total}`，page 从 1 开始、默认 20、pageSize 1..100、ID 稳定升序。搜索 q 去首尾空白，空白视无筛选，最长 128；SQL 参数绑定，并把 `%`、`_` 当普通搜索字符处理。

### 4.1 当前身份、角色与有效权限

扩展 `GET /api/auth/me?systemCode=demo-engineering-app`；省略 systemCode 保持现有响应完全不变，登录响应也保持不变。有参数时增加 `authorization`，不增加第二个返回身份/工作区的接口。

```json
{
  "authorization": {
    "systemCode": "demo-engineering-app",
    "roles": [
      {"id": 10, "name": "示例角色", "direct": true, "inherited": false,
       "inheritedFromRoleIds": [], "appliesToSystem": true}
    ],
    "effectivePermissions": [{"id": 20, "code": "request:read", "name": "查看申请"}],
    "globalAdministrator": false
  }
}
```

示例只展示新增片段；employee/workspaces/defaultWorkspaceKey 仍存在。roles 为直接及传递可达角色的去重集合；一个角色可以同时直接分配且被其他根角色继承，两个布尔值允许同时为 true。inheritedFromRoleIds 是能到达它的其他直接分配根角色 ID，不枚举所有路径，排序去重。

角色不是按系统分配：保留全部来源，appliesToSystem 表示该角色自身或继承闭包中有目标系统的配置权限，不代表组织策略下仍有效；effectivePermissions 才是实时有效集合。全局特权可以没有对应角色，globalAdministrator 不授予绕过 DISABLED 的能力。以上表达待 Q1 确认。

只允许读取当前身份，不接受 employeeId；无需 management:read，但必须可进入目标系统。管理员查询他人仍走现有 `/api/employees/{employeeId}/roles` 和 `/effective-permissions?systemCode=...`，其响应与管理范围不变。前端用于工作区身份/授权摘要。

### 4.2 单个菜单/按钮权限判断

新增 `GET /api/auth/me/permission-check?systemCode=...&permissionCode=request:approve`，参数均必填且非空，长度遵循现有系统码 64、权限码 128。

响应 `{systemCode,permissionCode,allowed}`；存在但无权限为 200 + allowed=false。复用 AuthorizationService 的同一计算，不赋予管理权限。菜单使用 `request:read`，按钮使用现有 `request:create/update/withdraw/approve/reject/delete`。不新增 menu:*、button:* 别名或无需求依据的 permission.type 字段。

BusinessPage 初次进入读取有效权限集合，批量渲染菜单与按钮；单项检查供单个控件刷新/演示，避免对每个按钮逐个请求。保留请求列表 allowedActions 兼容字段，使其与统一计算结果一致。状态/本人所有权仍决定逐行按钮及实际操作；请求失败应刷新授权状态，不能沿用旧 true。

### 4.3 部门逐层查询

扩展 `GET /api/departments`：

| 参数 | 意义 |
| --- | --- |
| view | directory（默认，保留旧原表目录）或 tree（正式组织树投影） |
| parentId | tree 下读取指定正式组织的直接子级；必须存在且在可见范围 |
| rootsOnly | tree 下 true 表示当前可见范围的根；与 parentId 互斥 |
| q | 名称/编码搜索；与 parentId 同用只搜直接子级；仅 q 则在可见节点内搜索 |
| page/pageSize | 两个视图均按现有方式分页 |

tree 无 parentId/q 时默认 rootsOnly=true；rootsOnly=true + q 搜根节点。directory 允许 q，不接受 tree 专属条件，错误组合为 400。旧目录默认仍只允许管理员；tree 才适用确认后的员工目录范围。

tree 的 item 为 `{id,code,name,parentId,organizationType,hasChildren}`。为展示现有真实根，允许 COMPANY 作为分组节点、DEPARTMENT 作为部门节点；“根”是可见范围根，部门管理员/普通员工可以直接以本部门为根，其 parentId 仍保留真实数据库值。hasChildren 只统计范围内的正式直接子级，不泄露不可见分支；不受 q 对子级名称的匹配影响。不能用 sourceParentName 充当可靠层级引用。

directory 响应保留原字段；tree 是显式选择的新投影，不把原表行悄悄改成树。前端保留原目录核对页，增加树形浏览与员工筛选。当前两层支持还是任意深层支持见 Q5，后者未确认前不宣称已承诺。

### 4.4 指定 API 调用权限判断

新增 `GET /api/auth/me/api-check?systemCode=...&operationId=approveRequest`；必填，operationId 限 128 字符。响应 `{systemCode,operationId,allowed}`，只表示系统准入及权限组合，不读取具体 requestId，不承诺操作执行成功。

首批覆盖四个已有 demo-* 申请系统，各有以下 8 个 operationId，不将权限平台管理动作混进业务系统权限：

| operationId | 所需权限（ALL） |
| --- | --- |
| listSystemRequests / getRequest | request:read |
| createRequest | request:create（保留当前行为，不额外要求 read） |
| updateRequest | request:read + request:update |
| withdrawRequest | request:read + request:withdraw |
| approveRequest | request:read + request:approve |
| rejectRequest | request:read + request:reject |
| deleteRejectedRequest | request:read + request:delete |

映射以 OpenAPI 已有 operationId 为键，禁止客户端提交所需权限。推荐本轮固定 ALL，不实现 ANY/嵌套表达式；空权限集、失效引用、缺映射均不可默认为允许。映射与实际业务检查共享同一操作需求定义/校验，契约测试保证两者一致。特别覆盖“有 create、无 read”仍可发起申请的现有后端行为（功能版 BusinessRequestService.java:90-99），不能为了页面流程顺手增加权限要求。目标操作始终再次进行实时权限、申请归属及状态检查。

推荐持久化映射而暂不开发映射管理页面，见迁移章节；若选择版本化代码配置，则取消映射表迁移，两版必须消费同一份定义并校验打包结果。前端在业务工作区“当前权限”区域提供 API 检查选择项，主页面仍批量消费权限集合。

### 4.5 指定部门员工查询

扩展 `GET /api/employees?departmentId=...&q=...&page=1&pageSize=20`，departmentId 可选，严格指向 DEPARTMENT；本轮默认只查直接归属员工，不加 includeDescendants。q 对姓名或 username 做包含搜索，组合条件为 `可见范围 AND 部门条件 AND (姓名匹配 OR 账号匹配)`，count 同样执行。

保留现有员工分页白名单及遮盖电话，不暴露密码、登录账户表和原始电话。普通员工仅启用员工，管理员沿用可查看停用员工的现状；全局管理员无 departmentId 时仍可核对未匹配组织员工。不存在部门 404；存在但越界 403；合法空结果/页码超过末页 200 空 items、保留筛选后 total。

确认 Q4 后才将员工列表与 tree 读路由开放给普通员工；员工详情、他人角色/有效权限、管理写入仍保持管理员边界。前端管理员工页、业务工作区同部门目录共用列表渲染和搜索分页，按钮按管理资格显示，后端资格校验不变。

### 4.6 错误和边界行为

| 情况 | 提案 |
| --- | --- |
| 未登录/员工已停用或无归属 | 401 AUTHENTICATION_REQUIRED；沿用会话失效处理 |
| 未知系统 | 404 SYSTEM_NOT_FOUND |
| 系统存在但不可进入 | 403 SYSTEM_ACCESS_DENIED，先于读取其中权限/API 明细 |
| 已准入但未知权限码 | 404 PERMISSION_NOT_FOUND（新增错误码），区别于已知权限的 allowed=false |
| 已准入但未知 operationId/系统未配置该 API | 404 API_NOT_FOUND（新增错误码） |
| 已知权限/API 但不满足规则 | 预查询 200 allowed=false；实际操作仍 403 PERMISSION_DENIED |
| 部门/员工不存在或越界 | 沿用 404 RESOURCE_NOT_FOUND / 403 PERMISSION_DENIED；不为新查询偷偷更改旧详情行为 |
| 参数为空/超长/非法组合 | 400 VALIDATION_FAILED |
| 依赖故障/映射损坏 | 503 AUTHORIZATION_UNAVAILABLE 或 SESSION_UNAVAILABLE；禁止降级为允许 |

所有自身接口的身份仅来自服务端；未知查询参数 employeeId 等禁止用于切换查询对象。继续沿用 `{code,message}` 错误体。
