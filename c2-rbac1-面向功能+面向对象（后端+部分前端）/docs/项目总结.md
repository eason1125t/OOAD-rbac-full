# C2 项目总结

更新：2026-11-22。本文统一说明目标、已完成功能、实现方法、两版差异和后续工作。运行参数维护在[部署说明](../部署/README.md)，测试命令、结果和部署后验收维护在[测试说明](../测试/README.md)。

## 1. 我们完成了什么

C2 在 C1 员工、角色、权限和申请管理基础上实现 RBAC1：用户直接拥有角色，角色可以继承其他角色，最终权限还受业务系统准入和组织策略约束。我们保留面向功能和面向对象两套后端，用相同接口、前端和测试对照它们组织业务的方式。

用户从 /func/ 或 /oo/ 登录，选择管理或业务工作区。管理员维护组织、员工、角色、授权和继承；业务用户查看自身权限、查找范围内部门员工，并完成公司或部门申请。没有加入课程、教师、学生等无关业务。

| 完成内容 | 用户能观察到的效果 | 怎样实现 |
| --- | --- | --- |
| 原 RBAC0 管理 | 员工、角色、权限及两类分配关系维护 | 保留原模型、管理员资格和范围校验 |
| RBAC1 继承 | 多级、多路径继承，区分直接/继承来源 | 直接边入库，角色闭包展开和去重；拒绝自继承、循环和跨归属 |
| 组织策略与实时撤权 | 停用立即限制；重开后按来源重授 | 每次读取当前授权；同一有效来源满足所有适用组织策略 |
| 申请生命周期 | 发起、查看、修改、撤回、审批、驳回、本人逻辑删除 | 查看权和动作权分开，锁定记录后复核本人边界与状态 |
| 八项统一身份能力 | 身份/工作区、角色权限、权限判断、部门树、API预查询、员工查询与资料 | 扩展已有入口，集中可信身份和授权计算 |
| JWT 认证 | 页面恢复、多标签页协调、分版登录和退出 | RS256、独立 sid、严格刷新轮换；不把权限固化到JWT |
| Excel与日志 | 三份原表分页核对、电话遮盖、申请日志对应 | POI、来源标记、分页、事务最终结果审计 |
| 工程交付 | 同一契约、49组图件、双版测试、镜像和部署工具 | OpenAPI、Apifox、CloneFactory、JaCoCo、Playwright、Docker/Swarm |

本项目允许有审核权限的申请人审核本人申请；撤回为终态；只有本人能删除已驳回申请。这是当前需求，没有自动加入 RBAC2 职责分离约束。

## 2. 两套后端怎样组织代码

共同流程为：Controller 校验 HTTP 输入 → 取得可信员工身份 → Service 组织用例 → 统一授权 → 规则与存储 → 响应。Controller 不自行展开角色或判断组织策略，认证凭证与业务授权分开，两版保持相同行为。

| 对照 | 功能版 backend-func | 对象版 backend-oo |
| --- | --- | --- |
| 组织方法 | Service 按步骤编排，规则函数接收显式数据 | Service 协调事务与外部协作，对象维护自己的行为 |
| 角色图 | Graph 数据快照＋静态 Rules | RoleHierarchy 持有不可变快照并计算 |
| 申请状态 | Service 检查状态并设置字段 | BusinessRequest.rename/approve/withdraw 等方法维护状态 |
| 存储 | Service 直接依赖仓储较多 | 申请经 RequestRepository、RequestSystems、RequestAccess 窄端口协作 |
| 取舍 | 流程直观；复杂用例容易使Service变长 | 规则集中、可独立测试；类型与映射需要维护 |

对象版是局部领域设计，没有整体重写为 DDD。RoleHierarchy 负责计算，不负责保存继承边。“满血模型”只是隔离内存小样，观察对象进一步承担装载/保存职责的代价；不是第三套线上后端，也不表示性能更好。详见[三模型比较](../三模型比较/README.md)。

### 一次继承修改

检查操作者管理资格 → 取得全局图写锁 → 读取当前边 → 校验双端范围、同归属、自继承及幂等 → 从 junior 检查到 senior 的可达性，防止闭环 → 校验授权影响 → 保存并提交。先锁后读与数据库事务隔离防止并发新增共同成环，不可变Map本身不能提供跨进程保证。

### 一次申请审批

锁定申请 → 从数据库记录确定所属系统 → 检查当前查看权＋审批权 → 状态转换 → 保存 → 按事务最终结果审计。功能版在Service内判断，对象版由BusinessRequest执行行为。客户端字段不能覆盖服务端确定的申请人、系统或状态。

### 一次有效权限计算

从员工直接角色展开继承闭包，汇总目标系统权限，再应用系统准入、组织停用和同源重授约束，按有效来源去重。删除唯一角色或继承路径后，原登录下一次操作拒绝；仍有其他合法路径则继续允许。全局管理员也不能绕过组织DISABLED。前端按钮和权限预查询只提供当前结论，实际操作仍重新检查记录、状态和权限。

## 3. 八项接口怎样接入原项目

参考文档的功能含义映射到当前员工、组织和申请模型，保留原响应与管理员边界，没有照搬其他业务字段。唯一主契约为[OpenAPI 2.5.0](../api/openapi.yaml)，详细参数、响应和例子见[八项能力契约](../api/统一身份鉴权接口契约.md)。

| 编号 | 接口 | 当前用途 |
| --- | --- | --- |
| ID-01 | POST /api/auth/login | 账号密码登录，身份/工作区＋访问JWT，刷新凭证仅Cookie |
| ID-02 | POST /api/auth/logout | 撤销当前sid并清理Cookie，其他独立登录不受影响 |
| ID-03 | GET /api/auth/me | 不传systemCode保留身份/工作区；传入后增加系统角色来源及有效权限 |
| ID-04 | GET /api/auth/me/permission-check | 按systemCode和permissionCode判断一个前端权限 |
| ID-05 | GET /api/departments | 保留管理员directory；新增tree、根/直接子级、hasChildren、搜索分页 |
| ID-06 | GET /api/auth/me/api-check | 按systemCode和operationId预查询API权限 |
| ID-07 | GET /api/employees | departmentId、姓名/账号搜索、分页与当前数据范围 |
| ID-08 | GET /api/employees/{employeeId} | 管理员查询范围内资料；普通用户自身资料使用me |

认证辅助入口保留 GET /api/auth/csrf，JWT新增 POST /api/auth/refresh。浏览器地址加/func或/oo前缀，网关转发时去前缀。

角色同时表达direct、inherited、来源根角色ID及与系统的相关性；角色涉及某系统不等于策略处理后有效。前端复用request:*：查看菜单用request:read，按钮用相应写权限；allowedActions继续表达具体申请可执行动作。

API映射固定ALL。首批demo-company-app、demo-engineering-app、demo-finance-app、demo-company-b-app各八个申请操作，共32操作、52条权限要求；Flyway V9新增两表。RequestOperation供映射和实际入口共用定义；预查询不判断具体申请的归属或状态。初始化不会把已撤销的角色、继承或组织策略恢复。

普通员工只见所属部门；直接归属公司者只见自身公司节点和直接归属员工，不扩大到全部部门。部门管理员见所管部门，公司管理员见所管公司及直属部门，全局管理员见全局。普通列表只给最小字段、排除停用员工；管理员资料电话仍遮盖。未知对象、参数错误和越界分别按契约返回404、400或403，不统一压成false或空列表。

## 4. 以前不用 JWT 时怎么做

早期采用Spring Security＋Session Cookie＋Spring Session Redis。账号密码与员工资格校验成功后创建服务端Session，保存可信员工ID；浏览器自动带本版Session Cookie，Spring Security从Redis恢复身份。写入通过Session CSRF保护，退出使该Session失效，闲置超时30分钟。

当时Session只提供身份，Service同样从MySQL读取当前角色、继承和组织策略。因此实时撤权在JWT前已经具备。迁移前先把“获取可信身份”与“执行业务授权”拆开，之后替换凭证生命周期，保留原业务、工作区、接口路径和两版设计。

| 内容 | 原Session | 当前JWT |
| --- | --- | --- |
| 业务请求 | Session Cookie恢复服务端身份 | Bearer验签并查询Redis sid |
| Spring Security | 会话恢复、CSRF和请求保护 | 保留，请求上下文不持久化到HttpSession |
| Spring Session Redis | 保存会话，30分钟闲置续期 | 依赖和Session配置已移除 |
| Redis服务 | 会话存储 | 保留，保存登录、当前刷新摘要和已消费摘要 |
| 浏览器 | Session Cookie | 访问JWT仅内存；刷新凭证仅HttpOnly Cookie |
| 有效期 | 闲置续期 | 访问最长15分钟，单次登录绝对8小时，刷新不延长上限 |
| 退出/撤权 | 失效当前Session；授权实时读取 | 撤销当前sid；授权实时读取，不使用tokenVersion |
| MySQL | 员工、账号、角色、继承、策略、申请 | 保留；JWT无用户版本字段或新迁移 |

## 5. 当前 JWT 怎样运行

登录复用密码哈希与员工资格校验，创建安全随机sid并签发RS256访问JWT。业务请求检查固定算法、签名、issuer、audience、sub、sid和有效期，再核对Redis登录及最新员工状态，转为可信员工ID后执行现有授权。JWT不携带可替代数据库的权限快照，不宣称认证完全无服务端状态。

刷新使用本版HttpOnly Cookie和Cookie CSRF，每次成功都轮换随机凭证；旧刷新凭证再次使用会撤销该次登录。同账号可多浏览器独立登录，退出只撤销当前sid，两版也独立。认证存储故障返回明确错误，不伪装成已撤销。

同版多标签页通过SharedWorker串行协调登录/刷新/退出，访问JWT只在Worker内存。页面刷新通过Cookie恢复；JWT和刷新凭证不放WebStorage、URL或日志。只有明确的访问过期允许刷新后重试一次；403、503、断网和结果不确定的写入不自动重放。生产使用HTTPS和Secure Cookie。

两版库、密钥、issuer/audience、Cookie及Redis namespace隔离；同版各副本使用稳定一致的密钥。后续其他系统联调还须约定受众、公钥分发、网关和在线撤销检查；本轮没有开放CORS，也未建设通用SSO/OIDC平台。

## 6. 工程方法与代码依据

- GRASP信息专家：图掌握可达性，申请掌握状态；Controller适配HTTP，Service控制用例与事务。
- 高内聚、低耦合与受保护变化：可信身份、授权、持久化、审计分别归口，对象版申请经窄端口隔开技术细节。
- Creator与映射分开：掌握可信数据者创建业务对象；CloneFactory负责同名同类型字段映射，PATCH优先copyNotNull，转换和敏感字段显式处理。
- MySQL/JPA/Flyway V1—V9保持关系与迁移一致；图写锁和申请行锁处理并发。
- OpenAPI统一外部行为，Apifox协作调试；JUnit、真实MySQL/Redis和Playwright分层验证，JaCoCo、命令TXT与失败/成功批次独立归档。
