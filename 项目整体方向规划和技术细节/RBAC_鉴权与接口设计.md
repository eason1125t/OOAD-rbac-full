# RBAC 鉴权与接口设计

2026-11-14 · C1、C2、C3 共用设计。适用于面向功能和面向对象两条实现线。

已确认采用 **Spring Security 请求授权 + 统一授权 Service**。管理端按资源和分配关系设计 API，业务模拟端按具体业务动作设计 API。本文的路径、字段和错误码用于详细设计，后续按模块写入 `api/openapi.yaml`。参见 [项目需求总览](../项目需求总览.md)、[技术规范](./RBAC_Technical_Conventions.md) 和 [阶段开发规划](./RBAC_Development_Plan.md)。

## 一、鉴权设计

### 1. 登录会话提供员工身份

**实现方式。** 后端核验本地账号密码，使用 Spring Security 的 `PasswordEncoder` 校验 MySQL 中的密码哈希。Spring Session 把会话保存在 Redis，浏览器携带会话 Cookie。请求到来时，由 Spring Security 恢复登录身份并取得关联的员工 ID。Redis 会话保存身份和必要会话状态，角色和权限由授权 Service 按当前 MySQL 数据计算，沿用项目禁用权限 version 的约定。

**目的与优点。** 服务端掌握操作人，退出或过期时会话失效。登录与权限分配各自维护，管理员撤权后员工可以继续登录，后续请求立即按最新关系判断。

**例子。** 员工 42 登录后提交 `POST /api/requests/301/approve`。路径中的 301 是申请 ID，操作人 42 来自服务端会话。提交体无需包含操作人的员工 ID、角色或权限编码。

两个独立前端采用同源路径和共用 Cookie 会话。保留 CSRF 校验，写操作按契约提交 CSRF 令牌，登录前取得令牌，登录或退出后按配置重新获取。Cookie 名称与令牌获取方式在登录模块落定。 [Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)

后端提供默认工作区和当前可进入的工作区列表。管理员默认进入管理平台；员工依次采用可进入的部门默认系统和公司默认系统，无可用项时展示空状态。顶部下拉改变当前系统路由，账户与会话保持一致。C2、C3 沿用导航，C3 若引入角色激活则使用独立操作。

### 2. 固定权限在 HTTP 请求入口检查

**实现方式。** 在 Infrastructure 的 `SecurityFilterChain` 中用 `authorizeHttpRequests` 集中登记「HTTP 方法 + 路径 → 权限编码」。固定权限路由通过 Spring Security 的 `AuthorizationManager` 调用统一授权 Service。登录和令牌获取等入口逐一登记，对需业务对象判断的用例明确登记为已登录可进入、由 Service 完成授权，未登记的业务 API 默认拒绝。

**目的与优点。** 新接口需要什么权限可以从配置中集中核对。请求在进入 Controller 前即可被拒绝，常规请求授权直接使用框架的过滤器链。

**例子。** `GET /api/employees` 要求 `employee:read`，`POST /api/employees` 要求 `employee:write`。员工只有读取权限时，第一个请求通过，第二个返回 403，创建逻辑不会运行。 [Spring Security 请求授权](https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html)

### 3. 统一授权 Service 实时查权

**实现方式。** 授权入口接收可信的员工身份和由后端指定的权限编码，动态约束若启用可再接收会话激活角色。按阶段使用 Spring Data JPA Repository 查询员工—角色、角色—权限，以及新增的继承和约束数据。权限编码用稳定的 `资源:动作` 格式。管理界面可以显式配置角色与权限分配，Excel 权限清单保留原文用于展示。

**提交与读取边界。** 分配与撤销在 Service 事务中完成，接口在事务提交成功后返回 204。受保护请求从 MySQL 主库读取已提交的授权关系，使用本次请求的读取边界，避免复用旧事务快照。Redis 会话用于恢复身份及必要会话状态，固定权限判定每次重新查询。C1 的实时生效口径是变更提交后发起的下一次请求。已经通过鉴权的在途请求可按原流程完成。[MySQL InnoDB 一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

**C1 查询方式。** 固定管理权限按员工 ID 和目标权限码查询有效分配路径。业务权限还要纳入业务系统 ID 和组织范围。同一个权限码可用于多个系统，每套系统中的授权分别生效。只判权时查路径是否存在，展示权限时按需查列表。逻辑表对权限及分配关系设置与归属一致的唯一约束。C2、C3 延续统一入口，在内部纳入继承和约束。

**撤权语义。** 管理员身份只决定其当前能否执行分配。管理员被撤权或离职后，历史上已提交的分配继续有效。若组织取消某业务系统的某项权限，授权 Service 按目标组织、系统和权限判断其是否仍可授予。取消后，范围内的审批从下一次请求起失效，即使存在多条角色路径。重新开放后超级管理员恢复默认操作权，其他账号需要按范围和角色显式重授。其他组织、系统或动作继续按各自配置计算。参见 [C1 组织权限停用与重新开放](<../c1-框架-rbac0-结构化+面向功能/docs/组织权限停用与重新开放.md>)。

**目的与优点。** 框架负责接入与拦截，权限计算集中在可测试的业务入口。各阶段与两种实现都能复用路由、权限名称和调用约定。

**例子。** 员工 42 通过「审批员」角色得到 `request:approve`。管理员撤销这条唯一授权路径并提交后，员工 42 保持同一会话发送下一次审批，得到 403。若另有有效路径，审批权限继续有效。实时授权的验收以变更提交后的下一次请求为准。

### 4. 依赖资源的规则在业务 Service 检查

**实现方式。** 用例需要读取目标对象才能判定权限时，在应用 Service 加载资源并显式调用授权守卫，然后检查业务范围及状态，最后执行写入。固定权限已经在请求入口检查的场景直接进入业务状态校验。每个用例明确同一权限条件的检查位置，避免重复查询。

**C1 的组织范围。** 公司管理员的管理范围为本公司及下属部门，部门管理员的范围为本部门。管理列表在数据库查询及计数时应用组织范围。对单条数据和分配关系，Service 校验当前操作者的范围、目标员工和角色的归属，以及权限是否已开放给该范围。部门或公司管理员可以维护自己的定义，上级共享定义由超级管理员维护。对业务端，服务端依据业务系统的公司或部门归属判断准入，并校验目标业务记录属于该系统。普通员工和部门管理员可进入其部门及所属公司的系统，公司管理员可进入本公司及下属部门的系统。

**超级管理员。** 统一授权 Service 按服务端确认的管理员身份允许其进入所有系统，并默认具备各系统仍开放的业务操作权限。组织已取消的操作在对应范围内停止执行。业务 Service 仍校验资源存在及归属一致性、参数和业务状态。客户端通过切换实际登录账号展示角色差异。

**目的与优点。** 对象归属和业务状态可以使用同一次用例读取的对象。C1 审批由 Spring Security 检查会话，业务 Service 从申请记录确定系统，再调用统一授权 Service 检查该系统的准入和 `request:approve`。同一权限条件在一次调用中检查一次。

**例子。** A 公司工程部的审批员有 `request:approve`，可以在工程部系统审批，但请求同公司另一部门专属系统的申请时得到 403。超级管理员可以审批两边的待处理申请。

### 5. 三个阶段的判权规则

同一个审批例子使用 `POST /api/requests/301/approve` 和 `request:approve`。以下示例演示非超级管理员的权限计算，各自准备组织范围内的独立待审批申请。

| 阶段 | 实现方式 | 例子 | 目的与优点 |
| --- | --- | --- | --- |
| C1 · RBAC0 | 取直接分配角色的权限并集 | 员工 42 直接分到「审批员」，审批通过。撤销唯一分配后拒绝 | 建立可重复演示的基础授权与撤权链路 |
| C2 · RBAC1 | 直接角色加上可达的继承角色，汇总权限并去重。新增继承边时拒绝自继承和环路 | 「主管」继承「审批员」，只分到「主管」的员工也能审批。删除唯一继承路径后拒绝 | 沿用现有审批调用，验证授权来源可以扩展到角色层级 |
| C3 · RBAC3 | 保留继承。静态约束在关系写入时检查。若确认动态互斥，在角色激活时校验，并在请求时按当前仍有效的激活角色计算权限 | 假设约定「发起员」与「审批员」互斥。若约束覆盖继承角色，新增继承边可能导致已有组合冲突，按 C3 确认的策略处理。若动态互斥纳入范围，可演示同时激活两者被拒绝 | 沿用同一业务入口，展示约束怎样影响授权来源和会话 |

面向功能版以读关系、展开角色、计算权限等步骤组织 Service。面向对象版由应用 Service 协调用例，角色层级和约束规则由相应领域对象或领域服务承担。两版共用接口契约、演示数据和预期结果。C3 是否包含动态互斥、静态约束覆盖哪些角色集合，以及变更后如何处理已有分配和会话，按阶段需求另行确认。参见 [C2 阶段需求](<../c2-rbac1-面向功能+面向对象（后端+部分前端）/阶段需求与验收.md>) 和 [C3 阶段需求](<../c3-rbac3-面向功能+面向对象+部分函数式设计（完整前后端）/阶段需求与验收.md>)。

## 二、接口设计

### 1. 管理端采用资源式接口

**实现方式。** 查询用 GET，创建用 POST，部分修改用 PATCH。把员工—角色、角色—权限各自视为可单独定位的关系资源，用 PUT 建立关系、DELETE 撤销关系。增长型列表接收 `page`、`pageSize`，返回 `items` 和分页信息。接口使用整数 ID，输入用 DTO，输出用 VO，Controller 用 `@Valid` 校验。员工电话按已确认规则默认遮盖。

**目的与优点。** 资源名和 HTTP 方法直接说明操作意图，同一分配操作可以安全重试，前端的列表和分配组件也容易复用。

**例子。** `PUT /api/employees/42/roles/7` 使员工 42 拥有角色 7。重复请求可返回 204，关系仍只有一条，由数据库唯一约束兜底。对存在的员工和角色重复撤销已不存在的分配，也可返回 204。员工或角色本身不存在时返回 404。该幂等口径作为详细设计默认值。 [HTTP 语义规范](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods)

| C1 用例 | 接口示例 | 鉴权要求示例 |
| --- | --- | --- |
| 登录、当前员工、退出 | `POST /api/auth/login`、`GET /api/auth/me`、`POST /api/auth/logout` | 登录验凭据。当前员工与退出要求有效会话 |
| 查看员工、部门、Excel 功能权限清单 | `GET /api/employees`、`GET /api/departments`、`GET /api/permission-catalog` | `employee:read`、`department:read`、`permission-catalog:read` |
| 员工、角色、实际权限维护 | 例如 `PATCH /api/employees/{employeeId}`、`POST /api/roles`、`GET /api/permissions` | `employee:write`、`role:write`、`permission:read` |
| 员工分配、撤销角色 | `PUT`、`DELETE /api/employees/{employeeId}/roles/{roleId}` | `employee-role:write` |
| 角色分配、撤销权限 | `PUT`、`DELETE /api/roles/{roleId}/permissions/{permissionId}` | `role-permission:write` |

C1 的超级管理员、公司管理员和部门管理员可按各自范围写入两类关系。入口检查管理端准入和对应的写入权限，Service 检查关系两端的组织范围和可授予权限。检查适用于新增、替换和移除，也适用于通过角色编辑改变已有分配的效果。仅有 `request:approve` 的审批员调用分配接口时得到 403，数据库中的分配关系保持原样。

C2 沿用表中已有路径，新增如 `GET /api/roles/{roleId}/parents` 与 `PUT`、`DELETE /api/roles/{roleId}/parents/{parentRoleId}`。这里 `parentRoleId` 表示被当前角色继承、提供权限的角色。员工有效权限可用 `GET /api/employees/{employeeId}/effective-permissions` 查询，按后台管理权限保护。C3 新增如 `GET`、`POST /api/constraints`；若启用动态互斥，可用 `PUT /api/auth/me/active-roles` 更新当前会话的激活角色集合，由后端验证可激活范围和约束。新增接口按阶段录入契约和鉴权映射。

### 2. 业务模拟采用动作接口

**实现方式。** 建议用 `GET /api/business-systems` 返回当前账号可进入的系统。用 `POST /api/requests/{requestId}/approve` 表达审批动作，操作固定对应 `request:approve`。Controller 校验 ID 后调用审批 Service。Service 从申请记录取得业务系统归属，在事务内检查该账号能进入此系统并具有该系统的审批权限，随后校验业务状态并更新。

**目的与优点。** 一个动作有独立参数和权限要求。业务前端能够分别呈现授权结果与业务执行结果，三阶段可直接复用操作页面和测试用例。

**例子。** 员工 42 获得审批权限后请求审批 301。成功返回 200，结果示例为 `{"authorization":"GRANTED","execution":"SUCCEEDED","requestId":301,"status":"APPROVED"}`。对同一申请再次审批时，权限检查仍通过，但业务状态冲突，返回 409。

| 审批请求情况 | HTTP 与示例错误码 | 页面状态 |
| --- | --- | --- |
| 会话无效，请求已通过适用的 CSRF 检查 | 401 · `AUTHENTICATION_REQUIRED` | 鉴权未完成／业务未执行 |
| 缺少审批权限 | 403 · `PERMISSION_DENIED` | 鉴权拒绝／业务未执行 |
| 申请所属业务系统超出可进入范围 | 403 · `SYSTEM_ACCESS_DENIED` | 鉴权拒绝／业务未执行 |
| CSRF 校验失败 | 403 · `CSRF_INVALID` | 安全校验失败／业务未执行 |
| 找不到申请，无法确定系统归属 | 404 · `REQUEST_NOT_FOUND` | 鉴权未完成／业务未执行 |
| 有权限，申请已审批 | 409 · `REQUEST_ALREADY_APPROVED` | 鉴权通过／业务执行失败 |
| 授权数据服务临时不可用 | 503 · `AUTHORIZATION_UNAVAILABLE` | 鉴权未完成／业务未执行 |
| 有权限且审批成功 | 200 | 鉴权通过／业务执行成功 |

错误体统一包含稳定的 `code` 和可显示的中文 `message`。业务模拟前端按错误码呈现状态，区分同为 403 的 CSRF 拒绝和权限拒绝。非法请求参数使用 400，前端显示校验错误。审批先读取申请的归属，完成系统准入和动作授权后才检查业务状态或写入。

**错误处理位置。** Infrastructure 的 `AuthenticationEntryPoint` 输出未认证的 401，`AccessDeniedHandler` 区分缺权和 CSRF 失败的 403。固定权限查询发生在 Controller 之前，已识别的授权数据临时不可用异常由安全过滤器链映射为 503，并终止请求。业务状态冲突由应用层按契约返回 409。会话过期的写请求可能先命中 CSRF 校验并返回 `CSRF_INVALID`。前端收到该错误后，可通过 `GET /api/auth/me` 判断是否需要重新登录或重新获取令牌。[Spring Security 过滤器架构](https://docs.spring.io/spring-security/reference/servlet/architecture.html) · [CSRF 与会话超时](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html#csrf-timeouts)

### 3. 用 OpenAPI 管理公共契约

**实现方式。** 在 `api/openapi.yaml` 记录 `operationId`、请求参数与模型、会话 Cookie 安全方案、各状态码和示例。会话 Cookie 用 `type: apiKey`、`in: cookie` 描述。操作所需 RBAC 权限写在操作说明，运行时以 Spring Security 的路由映射和授权 Service 执行。校验 YAML 后生成 UTF-8 JSON，Apifox MCP 用于读取、审查和回读。同步按项目技术规范执行。

**目的与优点。** 前端、后端和测试使用同一份契约。C2、C3 各自的两种后端实现可以共享请求样例和契约测试。

**例子。** `approveRequest` 描述 `POST /api/requests/{requestId}/approve`、整数路径参数、Cookie 会话和 CSRF 请求头，并列出 200、400、401、403、404、409、503。操作说明标明 `request:approve`，测试核对缺权返回 `PERMISSION_DENIED`。 [OpenAPI 规范](https://spec.openapis.org/oas/v3.0.4.html)

## 三、复用与验收

| 复用内容 | 跨阶段验收例子 |
| --- | --- |
| 登录会话、授权入口、错误结构 | 用同一登录和退出用例。已退出的会话无法执行受保护操作 |
| 路由、权限编码、业务返回格式 | 三阶段用同一审批动作和同一权限码，页面可用同一套状态映射 |
| 实时授予与撤销 | 同一员工保持登录，用不同的待审批申请验证缺权 403、授予提交后 200、撤销提交后 403。分别覆盖撤销员工—角色及角色—权限，并确认拒绝时申请状态不变 |
| 多条授权路径 | 撤销其中一条路径并提交，仍有有效路径时，同一会话继续获准 |
| 授权管理入口 | 普通审批员调用任一关系写接口均返回 403，分配关系不变。管理员重复建立或撤销同一关系，按接口的幂等规则返回 |
| 组织范围与超级管理员 | 公司管理员可管理下属部门。部门管理员越部门查询或尝试分配上级管理角色时被拒绝。普通员工跨部门专属系统操作被拒绝，超级管理员可操作任意系统的待处理申请 |
| 安全过滤器与失败路径 | 通过实际过滤器链验证无会话的受保护 GET 返回 401、有效会话且缺权返回 403、缺失或过期 CSRF 令牌返回 403、授权查询临时不可用返回 503。核对错误码及受保护业务未执行 |
| 同阶段两版契约 | C2 两版共同测试继承、环路拒绝和多路径。C3 两版在同样的约束配置下得到相同的冲突、写入和授权结果 |
| 新增路由的登记规则 | 每条受保护 API 都有 OpenAPI 条目、鉴权配置或明确的 Service 检查位置，以及成功与拒绝用例。验证未登记的业务路由默认拒绝 |

进入详细设计时，先用审批场景定稿「路由 → 权限 → 授权位置 → 状态码 → 测试」，再按同一格式补齐员工、部门、角色、权限和两类分配的契约。先落实 C1 需要的接口，后续阶段按新增能力增补。

## 四、后续拓展方向

- **撤权与在途操作的并发控制。** 如果以后要求撤权阻止已通过鉴权但尚未写入的操作，需要明确撤权与业务写入的先后保证，再评估共用锁或串行化方案及其吞吐成本。
- **账号停用与已有会话。** 引入停用功能时，单独定义停用对现有会话的生效时点，再选择撤销会话或按请求检查账号状态。
