# RBAC 项目技术规范与开发流程

本文件配合《RBAC0、RBAC1、RBAC3 分阶段开发规划》使用。阶段规划定义交付范围，本文件定义开发方式、代码边界和检查条件。技术与代码规范以 `projectmgt-code-conventions` 的 `SKILL.md`、`references/apifox-sync.md` 和 `references/review-checklist.md` 为基线。本文明确的 RBAC 项目约定优先，其余可直接适用的规则沿用。原项目专用的包名、配置前缀、业务示例、认证地址及 Apifox 项目编号按 RBAC 项目的实际配置落地。

## 1. 已确定的技术与职责

| 项目 | 约定 |
|---|---|
| 后端 | Java 21、Spring Boot、Maven。使用 Spring Data JPA、Spring Security；数据库版本由 Flyway 迁移管理 |
| 前端 | Vue 3 + TypeScript。管理端和业务模拟端按各自用例设计，遵循 `front-end design` 的设计习惯。区分加载、空数据、错误、拒绝和成功状态 |
| 关系库 | MySQL。关系数据库访问统一通过 Spring Data JPA Repository。业务代码严禁直接使用 JDBC、`JdbcTemplate`、Spring Data JDBC 或 MyBatis |
| JDBC 依赖边界 | 保留 MySQL JDBC 驱动与 JPA、Flyway 所需的底层连接能力。审查重点是业务代码和数据访问适配器是否绕过 JPA Repository |
| Redis | 通过 Spring Session 保存服务端登录会话。需要会话角色激活时，可以在会话中保存激活角色 ID。授权关系与规则以 MySQL 为准，初期直接查当前数据来判权 |
| 身份认证与授权 | Spring Security 在 Infrastructure 层接入认证及请求拦截；Service 统一判断当前员工对目标操作是否有权限。采用实时授权，权限变更和凭证有效性均按各自规则处理，授权逻辑禁用权限 `version` 方案 |
| RBAC0 登录来源 | 自建账号密码登录与演示账号，作为 RBAC 项目对附件统一认证约定的覆盖。登录账号关联员工，由 Spring Security 核验凭据 |
| 接口设计 | 使用 Apifox，MCP 参与读取、审查接口契约与回读验证。仓库的 `api/openapi.yaml` 为主契约 |
| 需求与映射 | 模块确认阶段用 `grill-me` 梳理边界和验收场景。Java 同名同类型字段映射优先使用 CloneFactory |

Spring Data JPA 的 Starter 可以传递引入 Spring JDBC，项目禁用的是直接用它实现业务查询。Spring Session 支持用 Redis 保存服务端会话。参见 [Spring Boot SQL 数据访问](https://docs.spring.io/spring-boot/reference/data/sql.html) 和 [Spring Session Redis 指南](https://docs.spring.io/spring-session/reference/guides/boot-redis.html)。

## 2. 应用分层与编码约定

### 项目结构与抽象

- 全项目保持结构规范、目录整洁、代码可读、职责清晰和易于扩展。复用已经满足需求的组件，每个包、类和接口都应有明确职责。按用例组织代码，避免为预测中的需求预建多套层级或扩展点。
- 只有存在明确的架构边界或替换需求时才引入接口，例如 Spring Data JPA Repository、DDD 领域仓储端口或外部系统适配端口。职责明确的单实现业务类可直接使用具体类，避免为每个函数或 Service 机械增加接口、实现类和仅转发调用的包装层。
- JaCoCo 报告用于检查实际执行的生产代码。优先覆盖业务规则、异常分支和关键集成路径，审查时清理缺乏业务职责的包装层与未使用实现。Java 纯抽象接口方法本身没有可执行字节码，覆盖率取决于实际新增且未覆盖的实现代码。

### API 层

- 接收请求的对象放在 `dto` 包，以 `DTO` 结尾。对外响应放在 `vo` 包，以 `VO` 结尾。Controller 使用 `@Valid` 做字段和跨字段校验，并负责 DTO → Command、Result → VO 的映射。
- API 不直接暴露 JPA Entity。增长型列表统一采用 `page`、`pageSize`、`total`。接口 ID 按附件约定采用整数类型，OpenAPI 标注为 `integer`。
- 错误响应包含稳定的业务 `code` 和可展示的中文 `message`。无有效登录凭据、已登录但未获授权、资源不存在、规则冲突分别按约定使用 401、403、404、409。基础设施故障单独定义错误响应，鉴权无法完成时拒绝执行业务操作。

### Service、领域对象和 Infrastructure

- **两条开发线共用接口契约和业务验收规则。** 面向功能版按业务过程组织读取、规则校验、保存和权限计算。面向对象版按 GRASP 分配职责，应用服务协调用例与事务，角色层级等领域对象或领域服务负责业务规则。
- **跨仓储写入以 Service 方法为事务边界。** 面向对象版应用服务依赖领域仓储和业务端口，Infrastructure 适配器调用 Spring Data JPA Repository。对象版的领域模型用业务术语表达状态和规则，对应的领域常量按附件规范归口。
- **授权有统一入口。** Spring Security 取得可信的员工身份，由 Service 权限守卫查询当前有效授权。业务模拟前端提交目标操作，角色和有效权限由后端解析。先判权再执行，前端分别展示鉴权和业务结果。
- **会话状态与正式授权分开管理。** Redis 会话支持过期和退出失效。若后续会话保存激活角色，授权时结合最新分配及继承关系校验其有效性。验证场景包括撤销唯一授权路径后，保持登录的员工下一次调用被拒绝。C2 两版共用 Redis 实例，并使用独立会话命名空间、Cookie 名和路径。各自的 MySQL 库保存业务及授权数据。
- **外部 HTTP 和日志沿用附件。** 若接入外部认证或其他服务，由 Infrastructure 的 `@HttpExchange` 客户端和适配器完成，Service 只依赖业务端口。业务日志归口 `LayerLoggingAspect`，按 RBAC 包名配置级别，日志省略凭据、会话标识、完整请求响应及敏感字段。

### RBAC0 登录与演示账号

- **账号与员工对应。** 项目自行提供登录入口。登录名唯一，登录账号关联员工记录。使用 Spring Security `PasswordEncoder` 校验密码，MySQL 只保存密码哈希。参见 [Spring Security 密码存储文档](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)。
- **登录与授权各自取数。** 登录成功后建立服务端会话，由 Spring Session 存入 Redis。管理端和业务模拟端使用同一后端登录机制；授权服务依据会话中的员工身份，通过 JPA 查询当前角色和权限。
- **演示数据。** 准备一组有管理权限的员工账号和一组普通员工账号，仅在演示环境初始化。初始密码通过演示环境配置提供，账号角色通过项目的员工—角色分配关系配置。验收覆盖登录成功与失败、退出失效、普通员工获权及保持登录时撤权。

### 映射、格式和测试

- 同名同类型字段优先 `CloneFactory.copy(...)`，PATCH 优先 `copyNotNull(...)`。派生字段、多来源值、类型转换和权限相关字段按白名单显式处理。修改 CloneFactory 注解后做 clean 构建并跑测试。
- C2（RBAC1）和 C3（RBAC3）的面向功能版与面向对象版均沿用 C1 的课程 CloneFactory 与 Maven 注解处理器配置。阶段构建验证生成源码，映射继续遵守各自的层边界和上述显式字段规则。
- Java 显式声明类型，按附件约定使用 Lombok、中文 Javadoc、常规分行和真实换行。遵循测试先行，先观察由目标行为缺失造成的失败，再实现并回归。
- 按需求编号关联测试。每个业务错误码有契约测试，按 ID 的操作覆盖不存在 ID。集成测试使用真实 MySQL，覆盖事务回滚、数据库约束、权限拒绝和撤权。C2 两版共用 HTTP 契约断言和验收场景，各自维护单元与集成测试，交付可执行代码及分版本结果。测试代码的课程约定见阶段开发方案。C2 已按用户要求在 `测试/` 重新整理并集中交付测试代码和说明，归档 JaCoCo 原始报告、结果图、实际执行命令和命令行输出 TXT；当前执行入口已切换到测试目录，完成标准见 [C2 收尾清单](<../c2-rbac1-面向功能+面向对象（后端+部分前端）/收尾清单.md>)。

## 3. 数据库与接口工作流

### MySQL 与陈氏 ER 图

1. 对照课程 Excel 整理“原表列 → 页面字段 → 数据字段”的映射。实体、联系、属性和基数使用陈氏表示法绘制。
2. 另交逻辑表结构，标明主键、外键和唯一约束。RBAC0 管理员工、角色、权限及两类关联，RBAC1 增加角色继承，RBAC3 按已确认的约束范围扩展。可以由数据库表达的不变量用约束兜底，环路、角色互斥等业务规则在对应业务入口校验。
3. Flyway 只追加新迁移，已执行的迁移保留原样。数据库约束错误在触发写入的适配器或 Service 转为稳定业务错误。普通保存按附件使用 `save`／`saveAll`，只有需要在当前边界捕获唯一约束时采用附件约定的例外。

### OpenAPI 与 Apifox

1. 在模块方案中先确认接口用例、请求和响应、权限要求、错误码及典型例子，再更新 `api/openapi.yaml`。
2. 用 Apifox MCP 读取已有接口和模型，核对命名、字段及前后端约定。校验 YAML，再按附件流程生成同步用的 UTF-8 `api/openapi.json`。
3. Apifox 操作优先走命令行。同步前核对 RBAC 项目 ID、脚本位置和完整契约。只有明确要求同步时，才按已配置脚本执行远端写入。涉及覆盖与删除未匹配资源时，先核对完整接口清单和影响范围。
4. 同步后检查接口和模型失败数为零，再通过可用的 MCP 刷新并回读路径、模型和中文标签。附件所示 MCP 用于读取和刷新，写入走已确认的导入流程。参见 [Apifox MCP 文档](https://docs.apifox.com/apifox-mcp-server)。

### GitHub

仅在用户明确要求时向 GitHub 推送项目进度。推送的提交说明采用简洁中文，写明实际完成的工作。

## 4. 瀑布阶段与模块确认流程

每个 RBAC 交付阶段按以下顺序推进。TDD 在实现阶段执行，最终验收按已确认的用例和接口契约核对。

| 工作阶段 | 输入 | 成果 | 检查条件 |
|---|---|---|---|
| 需求分析 | 教师要求、阶段规划、Excel、上阶段验收结果 | 功能范围、业务规则、用例、验收场景 | 核心场景和边界可判定，待确认项已标明 |
| 总体与详细设计 | 已确认需求与用例 | 界面设计、陈氏 ER 图和逻辑表、OpenAPI、Service 与模块设计、测试方案 | 页面、接口、数据和权限规则相互对应 |
| 实现与联调 | 已确认的设计和当前模块方向 | 前后端代码、迁移、联调数据、测试结果 | 先测试后实现，关键接口和页面联通 |
| 验收与交付 | 可运行版本和测试记录 | 阶段版本、启动说明、验收记录；双实现阶段附对比说明 | 核心用例可复现，双实现按共同用例验证 |

**每次启动下一个大功能模块前，先更新同一份 `开发方向细节.md`。** 用 `grill-me` 梳理真正影响实现的决策，结合已有设计和代码查证可确定的事项。文档按模块记录：

1. 模块名称、当前状态、目标和范围。
2. 所需输入、依赖和已确认的业务规则。
3. 具体开发步骤，以及前端、接口、Service、数据和测试会改哪些地方。
4. 交付物、可复现的验收场景和待确认问题。

文档状态依次为 **待确认 → 已确认 → 实现中 → 已验收**。用户确认后开始该模块实现。发现方向或交付范围有变化时，先更新同一份文件中对应模块的内容，保留关键变更记录，再按确认后的方向继续。

模块确认聚焦影响整体架构、核心业务规则或课程验收范围的决定。可逆的展示方式、示例数据和局部实现细节由开发者判断，在开发前说明处理方式及理由，并记录在对应模块方案中，随后按该方式推进。发现细节实际会改变公共契约、授权语义或已确认的验收条件时，按重大变更处理。

## 5. 建议补充确认的事项

| 事项 | 建议 |
|---|---|
| 版本、配置和复现 | 在首个模块方案中锁定 Spring Boot、MySQL、Redis、Node 等版本和启动方式。提交环境变量示例和演示数据，凭据通过本地或部署配置提供 |
| 两个前端的会话联调 | 优先确定管理端、业务模拟端与后端的部署关系。采用 Cookie 会话时，在接口设计中明确 Cookie、跨域凭据和 CSRF 处理，并测试退出和会话过期 |
| 工具与目标项目 | 开工前核对 `grill-me`、`front-end design`、CloneFactory 生成链路、RBAC 专用 Apifox 项目及 MCP 连接。附件中的旧项目配置仅作为迁移参考 |
| 同步交付标准 | 为同一功能维护一套 API 契约和验收数据。双实现用相同输入验证成功、拒绝、撤权及冲突，分别保留可运行结果 |
