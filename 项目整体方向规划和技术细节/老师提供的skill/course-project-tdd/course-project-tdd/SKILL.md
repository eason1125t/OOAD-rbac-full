# 课程项目管理系统 · 测试先行（TDD）

## 铁律

**没先看到测试失败，就不写实现代码。** 先写了实现？删掉重来 —— 不留作「参考」，不边写测试边改。

先写测试再实现，和先实现再补测试，看起来都「有测试」，但后者只是证明了代码现在的行为，从来没有证明过**这个测试能抓住那个 bug**。TDD 的价值就在这里。

例外只有三类，且**要先问用户**：一次性探索（例如 `prototype/` 这套界面原型）、生成代码、配置文件。

## 循环：RED → 验证失败 → GREEN → 验证通过 → REFACTOR

1. **RED**：一次只写**一个行为**的测试；名字说清行为；用真实代码，**不 mock**（除非依赖真的慢或外部）。
2. **验证 RED（必做）**：跑它，确认是**失败**（不是报错）、失败原因正是「功能还没实现」。
   测试直接通过 → 说明你在测已有行为，改测试；测试报错 → 先修错误，重跑到「正确地失败」。
3. **GREEN**：写**只够通过**的最小实现。不加功能、不顺手重构别的模块。
4. **验证 GREEN（必做）**：新测试过、**其他测试也都过**、输出干净（无 warning）。实现导致失败 → 修实现，不改测试。
5. **REFACTOR**：只有绿灯之后才去重、改名、抽函数；保持全绿。
6. 重复：下一个行为，下一个失败测试。

## 本项目四条硬约定

1. **需求编号就是测试名。** `docs/requirements.md` 里的 `Rxx` 编号是唯一真相；每个用例的 `describe`/文件名带上它（例如 `describe('R25b 学生的「我的成绩」页')`），收尾时能一眼看出哪条需求还没被测试覆盖。
2. **接口契约以 `api/openapi.yaml` 为唯一真相。** 请求/响应字段、分页（`page`/`pageSize`/`total`）、错误结构 `{ code, message, details? }` 都照它写测试；**每个 4xx 业务码至少一个用例**（`MILESTONE_RECORDED`、`CANCEL_WINDOW_CLOSED`、`WEIGHT_SUM_NOT_100` 等）。
3. **`prototype/` 是一次性原型，不是产品代码。** 不要把它改造成产品代码，也不要回头给它补 TDD —— 它已经完成「探索」的使命。产品代码另起目录（见 `references/stack.md`），从测试开始重写；原型只作为视觉与交互的参照。
4. **数据库层的不变量要测两遍**：领域单测（纯逻辑）+ 真实数据库的集成测试（唯一约束、外键、并发）。**不要 mock 数据库**；用临时库 + 每个用例事务回滚。领域规则和库约束是两道防线，都要有自己的测试。

## 先写哪一层

领域规则 → 仓储与数据库约束 → HTTP 接口契约 → 前端组件 → 端到端（只覆盖关键路径）。
每一层都遵守同一个循环。层次越靠里，测试跑得越快、越该覆盖得密。

## 反模式（写了就等于没测）

- **镜像断言**：期望值由被测代码（或它的 helper）算出来 → 两边同源，永远为真。期望值必须**独立推导**，用手写常量。
- **测 mock**：断言 mock 被调用几次，而不是断言真实行为。
- **变动探测器**：只测常量值、报错文案、私有结构 —— 改设计就红、真 bug 却抓不住。要测的是**依赖这个决定的真实行为**。
- **测框架**：断言「我注册的路由被调用了」这种是框架的测试，不是你的。
- **测试里泄漏实现细节**：测试一旦因为内部重构就红，就失去了它的意义。

写测试前先回答一句：**这条测试要防的是哪种破坏？** 答不出来就先别写。

## 收尾前清单

- [ ] 每个新增/修改的函数、接口、组件都有测试
- [ ] 每个测试都**亲眼看过它失败**（且因为正确的原因失败）
- [ ] 实现只写了够通过的最小代码
- [ ] 全部测试通过，输出干净（无 warning）
- [ ] `references/invariants.md` 里相关的业务不变量，都有对应用例
- [ ] 用例名里带上了需求编号

## 修 bug

先写一个**能复现**的失败测试，再走同一个循环。没有复现测试就不许「顺手修一下」—— 那个 bug 会回来的。
